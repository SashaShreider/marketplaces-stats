# IMPLEMENTATION.md

## 1. Назначение

Этот документ описывает технические требования и рекомендуемый порядок реализации backend согласно `SPEC.md`.

`SPEC.md` является источником требований к функциональности.

Этот документ описывает:

* структуру backend;
* интеграцию с OZON API;
* модель хранения данных;
* обработку финансовых операций;
* синхронизацию;
* REST API;
* тестирование;
* контрольные точки разработки.

Не следует реализовывать функциональность, которая не требуется `SPEC.md`.

---

# 2. Технологический стек

Использовать:

* Java 21;
* Spring Boot;
* Spring Web;
* Spring Data JPA;
* Hibernate;
* PostgreSQL;
* Flyway;
* Jackson;
* `RestClient` для HTTP-запросов к OZON API;
* JUnit 5;
* Testcontainers для интеграционных тестов с PostgreSQL.

Frontend на этом этапе не реализуется.

---

# 3. Общая архитектура

Использовать один Spring Boot application.

Логически разделить приложение на следующие части:

```text
API
 │
 ├── Analytics
 │
 └── Synchronization
          │
          ▼
   Marketplace Adapter
          │
          ▼
       OZON API
          │
          ▼
      Persistence
          │
          ▼
      PostgreSQL
```

Для OZON должна существовать отдельная интеграция.

В будущем должна быть возможность добавить:

```text
MarketplaceAdapter
 ├── OzonAdapter
 ├── WildberriesAdapter
 └── YandexMarketAdapter
```

При этом аналитическая часть не должна зависеть от конкретного API OZON.

---

# 4. Конфигурация OZON

Данные для подключения к OZON не должны быть захардкожены.

Использовать конфигурацию приложения/environment variables.

Необходимо предусмотреть как минимум:

```text
OZON_CLIENT_ID
OZON_API_KEY
```

На локальном этапе допустимо хранить их через `.env` или конфигурацию окружения.

Секреты не должны попадать в Git.

---

# 5. Работа с OZON API

Для получения финансовых данных использовать официальные методы OZON Seller API из документации, предоставленной пользователем.

В первую очередь необходимо изучить методы:

```text
/v1/finance/accrual/by-day
/v1/finance/accrual/types
```

Фактические URL, параметры запросов и структуру ответов брать из актуальной документации OZON, а не придумывать самостоятельно.

---

## 5.1. Получение финансовых данных

Синхронизация должна принимать:

```text
date
cursor / last_id
```

или соответствующие параметры согласно актуальной документации OZON.

Необходимо учитывать pagination.

Если OZON возвращает `last_id`/cursor для следующей страницы, необходимо продолжать запросы до получения всех данных за день.

Нельзя считать первый полученный ответ полным набором данных.

---

# 6. DTO OZON

API-модели OZON должны быть отделены от внутренних моделей приложения.

Например:

```text
ozon/
 ├── dto/
 │    ├── FinanceAccrualResponse
 │    ├── FinanceAccrual
 │    ├── Posting
 │    ├── PostingProduct
 │    ├── Delivery
 │    ├── DeliveryService
 │    ├── ItemFees
 │    └── ...
 │
 ├── OzonClient
 └── OzonAdapter
```

DTO должны максимально соответствовать JSON, который возвращает OZON.

Не следует помещать бизнес-логику в DTO.

---

# 7. Хранение исходных данных

Каждая финансовая операция OZON должна сохраняться в базе.

Необходимо сохранять исходный JSON ответа для каждой операции.

Для PostgreSQL использовать `JSONB`.

Это необходимо для возможности:

* повторно обработать исторические данные;
* изменить правила аналитики;
* проверить расхождения;
* исследовать новые поля OZON;
* не загружать данные повторно только из-за изменения логики приложения.

---

# 8. Модель данных

Минимальная структура:

```text
marketplace
    │
    ▼
seller_account
    │
    ▼
finance_accrual
    │
    ├── posting
    │      └── posting_product
    │              └── delivery_service
    │
    ├── item_fee
    │      └── item_fee_detail
    │
    └── non_item_fee

accrual_type
```

---

## 8.1. marketplace

Предназначена для поддержки нескольких маркетплейсов.

Поля:

```text
id
code
name
created_at
updated_at
```

Пример:

```text
OZON
```

---

## 8.2. seller_account

Представляет подключённый аккаунт продавца.

Поля:

```text
id
marketplace_id
name
client_id
api_key
created_at
updated_at
```

Для MVP достаточно одного аккаунта OZON, но модель должна позволять добавить несколько аккаунтов.

---

## 8.3. finance_accrual

Главная сущность финансовой операции.

Поля:

```text
id
seller_account_id
external_id
accrual_date
unit_number
accrued_category
total_amount
currency
raw_data
created_at
updated_at
```

`external_id` — это `accrual_id` из OZON.

Уникальность:

```text
seller_account_id + external_id
```

`unit_number` **не является уникальным**.

Одна продажа/отправление может иметь несколько финансовых операций.

Необходимо создать индексы для:

```text
seller_account_id + accrual_date
seller_account_id + unit_number
```

---

# 9. POSTING

Для финансовых операций категории `POSTING` создать отдельную сущность.

```text
posting
```

Поля:

```text
id
finance_accrual_id
delivery_schema
created_at
updated_at
```

Связь:

```text
finance_accrual 1 ─── 1 posting
```

---

# 10. Товары внутри POSTING

Один POSTING может содержать несколько товаров.

Создать:

```text
posting_product
```

Поля:

```text
id
posting_id
sku
quantity

seller_price
sale_price
sale_amount
sale_commission
commission
commission_ratio
coinvestment
bonus

currency

created_at
updated_at
```

Все денежные значения хранить как `NUMERIC`, а не `FLOAT`/`DOUBLE`.

Рекомендуемый тип:

```text
NUMERIC(19,4)
```

SKU хранить как `BIGINT`.

---

# 11. Логистика

Логистика находится внутри:

```text
posting.products[].delivery.services[]
```

Создать:

```text
delivery_service
```

Поля:

```text
id
posting_product_id
type_id
amount
currency
created_at
```

Связь:

```text
posting_product 1 ─── N delivery_service
```

Не следует жёстко зашивать конкретные `type_id` логистики в бизнес-логику, если структура API позволяет определить логистику по расположению данных.

---

# 12. ITEM

ITEM может содержать расходы, связанные с одним или несколькими SKU.

Создать:

```text
item_fee
```

Поля:

```text
id
finance_accrual_id
sku
quantity
created_at
```

Один `item_fee` может иметь несколько деталей:

```text
item_fee_detail
```

Поля:

```text
id
item_fee_id
type_id
amount
currency
created_at
```

Таким образом:

```text
finance_accrual
      │
      ▼
   item_fee
      │
      ├── detail
      ├── detail
      └── detail
```

Это важно, поскольку один ITEM может содержать несколько SKU и несколько типов расходов.

---

# 13. NON_ITEM

NON_ITEM может представлять расходы, которые не относятся к конкретному SKU.

Создать отдельную сущность:

```text
non_item_fee
```

Минимально необходимо сохранить:

```text
id
finance_accrual_id
type_id
amount
currency
created_at
```

Если фактический JSON OZON содержит дополнительные значимые поля, их необходимо сохранить.

Если структура поля пока недостаточно известна, исходный JSON уже должен сохраняться в `finance_accrual.raw_data`.

---

# 14. Типы начислений OZON

Не следует строить основную бизнес-логику на жёстко заданном списке `type_id`.

Использовать справочник:

```text
accrual_type
```

Поля:

```text
id
marketplace_id
external_type_id
name
description
created_at
updated_at
```

Уникальность:

```text
marketplace_id + external_type_id
```

Данные справочника получать из OZON API.

Например:

```text
1  → Acquiring
74 → StarsMembership
```

Конкретный список типов не должен быть захардкожен, поскольку OZON может добавлять новые типы.

---

# 15. Правила определения операций

## Продажа

Продажей считается `POSTING`, содержащий товар с положительным:

```text
sale_price > 0
```

Для отчёта:

```text
Количество = quantity
Сумма продаж = sale_price
```

Не использовать `total_amount` POSTING как сумму продаж.

`total_amount` отражает финансовый результат конкретной операции после применённых начислений/списаний.

---

## Возврат

Возврат определяется по:

```text
sale_price < 0
```

---

## Комиссия

Комиссия берётся из данных POSTING товара:

```text
sale_commission
```

Необходимо сохранять исходное отрицательное значение.

---

## Логистика

Логистика определяется по:

```text
posting.products[].delivery.services[]
```

Каждая услуга сохраняется отдельно.

Для отчёта сумма логистики рассчитывается как сумма соответствующих `delivery_service.amount`.

---

## Прочие расходы

К прочим расходам относятся финансовые операции, которые не являются:

* продажей;
* возвратом;
* комиссией;
* логистикой.

В частности, необходимо учитывать ITEM и NON_ITEM операции.

Необходимо сохранять `type_id`, чтобы в дальнейшем можно было определить назначение расхода.

---

# 16. К выплате

«К выплате» должно рассчитываться на основании полного набора финансовых операций OZON.

Нельзя автоматически использовать только:

```text
POSTING.total_amount
```

поскольку для одной операции могут существовать дополнительные ITEM/NON_ITEM начисления.
Нужно считать положительные и отрицательные  начисления 

Важно:

```text
К выплате ≠ Прибыль
```

В MVP себестоимость товара не учитывается.

---

# 17. Синхронизация

Создать отдельный сервис синхронизации.

Примерная логика:

```text
sync(dateFrom, dateTo)
        │
        ▼
получить данные OZON
        │
        ▼
обработать pagination
        │
        ▼
сохранить finance_accrual
        │
        ├── POSTING → posting → products → delivery
        ├── ITEM → item_fee → details
        └── NON_ITEM → non_item_fee
```

Повторный запуск синхронизации не должен создавать дубликаты.

Использовать:

```text
seller_account_id + external_id
```

как уникальный идентификатор финансовой операции.

# 19. Порядок разработки

Работу выполнять небольшими этапами.

## Этап 1 — проект

Создать:

* Spring Boot проект;
* PostgreSQL подключение;
* Flyway;
* базовую структуру пакетов;
* конфигурацию.

**Проверка:**

Приложение запускается и успешно подключается к PostgreSQL.

---

## Этап 2 — база данных

Создать Flyway migration для:

* marketplace;
* seller_account;
* accrual_type;
* finance_accrual;
* posting;
* posting_product;
* delivery_service;
* item_fee;
* item_fee_detail;
* non_item_fee.

**Проверка:**

Все таблицы и связи создаются корректно.

---

## Этап 3 — OZON API

Реализовать клиент OZON.

Сначала проверить получение реального ответа API без сохранения.

**Проверка:**

Получен реальный JSON OZON и корректно десериализован в DTO.

---

## Этап 4 — сохранение

Реализовать преобразование:

```text
OZON DTO
   ↓
Domain/Entity
   ↓
PostgreSQL
```

Сохранять также исходный JSON.

**Проверка:**

После синхронизации реальные данные присутствуют в PostgreSQL.

Необходимо вручную проверить:

* `accrual_id`;
* дату;
* `unit_number`;
* категорию;
* сумму;
* SKU;
* продажи;
* комиссии;
* логистику;
* ITEM;
* NON_ITEM.

---

## Этап 5 — повторная синхронизация

Запустить синхронизацию того же периода повторно.

**Проверка:**

Количество финансовых операций не увеличилось за счёт дубликатов.

---

## Этап 6 — аналитика

Реализовать расчёт:

```text
Продажи
Возвраты
Расходы
К выплате
```

Сначала проверить расчёт на конкретных известных операциях.

---

## Этап 7 — ежедневный отчёт

Реализовать:

```http
GET /api/analytics/daily
```

Проверить:

* отдельные дни;
* несколько дней;
* период с отсутствием операций;
* итог за период.

---

## Этап 8 — отчёт по SKU

Реализовать:

```http
GET /api/analytics/products
```

Проверить:

* один SKU;
* несколько SKU;
* продажи;
* возвраты;
* расходы, привязанные к SKU;
* расходы без SKU.

# 20. Тестирование

Необходимо тестировать не только Java-код, но и правильность финансовых расчётов.

Минимальные сценарии:

### Продажа

Проверить:

```text
quantity
seller_price
commission
delivery
total_amount
```

### Возврат

Проверить отрицательный `sale_price` и отображение положительной суммы возврата.

### ITEM

Проверить:

* несколько SKU;
* несколько `type_id`;
* корректное сохранение сумм.

### NON_ITEM

Проверить, что операция сохраняется и не распределяется искусственно по SKU.

### Несколько операций одного unit_number

Проверить, что они сохраняются как отдельные `finance_accrual`.

### Повторная синхронизация

Проверить отсутствие дублей.

### Аналитика

Сравнить результаты приложения с рассчитанными вручную значениями на небольшом наборе реальных данных.

---

# 21. Важные ограничения

Не создавать без необходимости отдельные сущности:

```text
Order
Sale
Return
Profit
DailySales
MonthlySales
DailyFinance
MonthlyFinance
```

Продажи и возвраты в MVP являются аналитической интерпретацией финансовых данных OZON.

Не создавать заранее агрегированные таблицы.

Аналитика должна строиться из сохранённых финансовых операций.

Не использовать `FLOAT`/`DOUBLE` для денег.

Не хранить бизнес-логику внутри OZON DTO.

Не связывать аналитику напрямую с JSON OZON — сначала данные должны быть нормализованы и сохранены.

---

# 22. Контрольные точки

После каждого этапа остановиться и проверить результат.

Ключевые контрольные точки:

```text
1. Spring Boot + PostgreSQL работают
        ↓
2. Flyway создаёт структуру БД
        ↓
3. OZON API возвращает реальные данные
        ↓
4. DTO корректно обрабатывают ответ
        ↓
5. Данные сохраняются в БД
        ↓
6. Повторная синхронизация не создаёт дубли
        ↓
7. Продажи/возвраты/расходы определяются корректно
        ↓
8. К выплате сходится с OZON
        ↓
9. Работает ежедневный отчёт
        ↓
10. Работает отчёт по SKU
        ↓
11. Все основные сценарии покрыты тестами
```

На каждом контрольном этапе необходимо сначала проверить текущий результат, и только после этого переходить к следующему этапу.
