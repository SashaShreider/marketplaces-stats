# Фронтенд

React-интерфейс сервиса аналитики маркетплейсов. Показывает финансы по дням и по
товарам, следит за состоянием данных и сам инициирует их догрузку.

Интерфейс написан на TypeScript, собирается Vite, оформлен Tailwind CSS. Он не
имеет собственного сервера: это статика, которую отдаёт тот же Spring Boot, что и
API. В собранном виде это **один файл** `index.html` со встроенными JS и CSS.

---

## Быстрый старт разработки

Нужен Node.js 22.

```bash
npm install
npm run dev            # http://localhost:5173
```

Backend при этом должен быть запущен отдельно, а на нём — разрешён источник
фронтенда, иначе браузер не примет сессионную куку:

```bash
APP_ALLOWED_ORIGINS=http://localhost:5173 docker compose up -d
```

| Скрипт | Что делает |
|---|---|
| `npm run dev` | Сервер разработки с горячей перезагрузкой |
| `npm run build` | Сборка в `dist/` одним самодостаточным `index.html` |
| `npm run preview` | Отдать собранное локально, без backend |
| `npm run typecheck` | Проверка типов без сборки (`tsc --noEmit`) |

Сборка проверяется типами и в Dockerfile: `npm run build` упадёт при ошибке в
TypeScript, поэтому «сломавшийся тип» не доедет до образа.

## Как устроен код

```
src/
├── main.tsx                  Точка входа: монтирование, подключение стилей
├── App.tsx                   Каркас приложения: сессия, маркетплейс, роутинг страниц
├── api/                      Работа с backend
│   ├── http.ts               HTTP-слой: сессионная кука, CSRF, ошибки RFC 7807
│   ├── client.ts             Типизированные методы REST API
│   └── mappers.ts            Ответ API → модель интерфейса
├── features/imports/         Поведение, связанное с загрузкой данных
│   ├── useImportRunner.ts    Запуск фоновых импортов и опрос их хода
│   └── useAutoSync.ts        Автоматическая догрузка: пустая база, недогруженные дни
├── components/               Всё, что рисуется
│   ├── ui/                   Примитивы: PageHeader, AnimatedNumber, MarketplaceLogo
│   ├── layout/               Каркас: Sidebar, TopBar
│   ├── auth/                 Экран входа и регистрации
│   ├── marketplace/          Подключение маркетплейса, пустое состояние
│   ├── finance/              Деньги: карточки, график, таблица, кольцо расходов
│   ├── sync/                 Состояние загрузки: индикатор у календаря, полоса ошибки
│   └── common/               Общие для страниц элементы: DateRangePicker
├── pages/                    Страницы целиком: OverviewPage, ProductsPage
├── styles/index.css          Tailwind и базовые стили
├── utils/                    Форматирование чисел и дат, слияние классов
└── types.ts                  Типы: DTO бэкенда и модель интерфейса
```

Два решения, которые стоит уважать:

**Папки сгруппированы по смыслу, а не по типу файла.** `components/finance`
содержит всё про деньги, а не «все .tsx». В плоском списке из двадцати файлов
понять, где что лежит, можно только чтением всех; здесь достаточно названия папки.

**Внутри `src` импорты абсолютные — через `@/`.** Так перенос файла не ломает чужой
код. Алиас описан в двух местах, и они обязаны совпадать: `tsconfig.json`
(`compilerOptions.paths`) и `vite.config.ts` (`resolve.alias`).

## Поток данных

Одну и ту же картину стоит понимать до правок, иначе легко сломать тихую
автоматику.

```
api/client.ts  ──►  api/http.ts (кука, CSRF)  ──►  Spring Boot
      │
      ▼
api/mappers.ts  DTO бэкенда → DayFinance (расходы становятся положительными)
      │
      ▼
pages/*  ──►  components/finance/*  рисуют
```

Ключевые решения, которые отличают этот интерфейс от обычного:

**Сессия в куке, а не токен в заголовке.** `fetch` всегда вызывается с
`credentials: 'include'`, поэтому пришлось разбираться с CORS и `SameSite`. Отсюда
требование `APP_ALLOWED_ORIGINS` при разработке и `COOKIE_SAME_SITE=None` +
`COOKIE_SECURE=true` при публикации по HTTPS.

**CSRF-токен берётся из куки `XSRF-TOKEN` и дублируется в заголовке.** Это делает
`api/http.ts`: перед изменяющим запросом токен берётся из ответа `/api/auth/csrf`, а
при `403` обновляется и запрос повторяется один раз. Ни один компонент об этом не
знает — работать с CSRF вручную не нужно.

**Адрес backend задаётся по приоритету:** значение с экрана «Настройки сервера»
(localStorage) → `VITE_API_BASE_URL` → в разработке `http://localhost:8080`, в
сборке — тот же origin. Всё это в одном месте, `api/http.ts`, функция
`resolveBase()`.

**Ответ API превращается в модель интерфейса в `api/mappers.ts`, а не на лету.**
Знак расходов приходит из API отрицательным, а в интерфейсе расходы положительные:
компонент, который считает «доход минус расходы», не должен догадываться о знаках.
Значит день приходит в готовом виде.

## Состояние данных и почему его видно рядом с календарём

Отчёт всегда сообщает состояние данных, даже когда отдаёт `200`:
`NOT_LOADED`, `PARTIAL`, `HAS_ERRORS`, `READY` плюс список недостающих, упавших и
неокончательных дней. Отчёт за период, который не загружался, — это не ноль, а
состояние; путать эти вещи нельзя.

Раньше эти сведения показывались широкой плашкой под шапкой, и она висела почти
постоянно: последние дни почти всегда неокончательные, потому что маркетплейс
досчитывает возвраты. Постоянная плашка обесценивает настоящие проблемы — когда
появится `HAS_ERRORS`, её перестанут читать.

Сейчас то же самое живёт рядом с календарём, в `components/sync/SyncIndicator.tsx`:

| Состояние | Что видно | Почему так |
|---|---|---|
| Идёт импорт | Крутящийся значок, «12 из 90 дней», процент | Пользователь ждёт результат — надо показать, что процесс идёт и сколько ещё |
| `HAS_ERRORS` | Значок с числом ошибок, клик повторяет загрузку | Данные неполны, надо понимать почему; автоматически такие дни не перезапрашиваются |
| Неокончательные дни | Значок обновления, клик уточняет | Рутина, а не проблема: уместнее один значок, чем баннер |

Важное следствие: **неокончательный день уточняется только импортом.** Бэкенд
помечает день окончательным, когда прошло `SYNC_MATURITY_DAYS` (по умолчанию 3) и
повторная загрузка подтвердила, что сумма не изменилась. Само по себе время
прохождения не делает день окончательным — поэтому уточнение инициируется явно.

## Автоматическая догрузка

`features/imports/useAutoSync.ts` берёт на себя рутину, о которой пользователь не
должен думать:

1. **Пустая база.** Не загружен ни один день → текущий период тянется сам.
2. **Недогруженные дни.** Есть хотя бы один день в `missingDays` → импорт запускается
   сам. Проверяется именно список недостающих дней, а не статус отчёта: один
   недостающий день из диапазона — тоже повод.
3. **История.** Когда текущий период закрыт, один раз догружаются **90 дней перед
   ним**, а не последние 90. Первые 30 дней уже загружены, и повторный запрос по
   ним только съел бы квоту.
4. **Свежие дни.** При возврате на страницу неокончательные дни уточняются
   автоматически, но не чаще раза в сутки.

Всё это возможно на фронте, потому что сервер идемпотентен: `daysToSync` отдаёт
только незагруженные, упавшие и неокончательные дни. Повторный запуск за 30 дней
берёт у OZON три-пять дней, а не тридцать, поэтому автоматика не расходует квоту
зря. Если загружать нечего, прогон заканчивается сразу, не потратив ни одного
запроса.

**Состояние автоматики живёт в `localStorage`** под ключами с префиксом `ma.`
(фаза, время последнего уточнения, отметка догона). Отметка догона ведётся по
самому периоду, а не одна на всё приложение: иначе, догнав один диапазон, мы
заблокировали бы догон любого следующего на паузу.

Два защитных ограничения, без которых автоматика становится вредной:

- **Пауза между попытками догона.** Если день не загрузился по причине, которую
  повтор не исправит, бесконечные попытки каждые пару секунд съедали бы квоту.
- **Отметка времени ставится только после успешного старта.** Иначе неудачный запуск
  считался бы выполненным, и автоматика замолчала бы до следующей проверки.

Порядок запусков обязателен: пересекающиеся импорты сервер отклоняет с `409`,
поэтому догрузка истории начинается только после того, как отработал текущий период.
На этот случай `useImportRunner` умеет присоединяться к уже идущему прогону вместо
ошибки.

## Импорты

Импорт фоновый: сервер отвечает сразу и считает прогресс в фоне, а интерфейс
опрашивает `GET /imports/{id}`, пока `inProgress == true`.

`features/imports/useImportRunner.ts` скрывает это за тремя функциями:
`startFinance`, `startCatalog`, `dismiss`. Он же:

- подхватывает уже идущий импорт после перезагрузки страницы;
- при `409` с `activeImportId` присоединяется к нему, а не показывает ошибку;
- держит `busy`, который гасит повторные клики.

Если импорт не запустился, `runner.error` объясняет почему: сообщение показывается
крупно, под шапкой. Это единственное уведомление о загрузке, которое осталось
вне календаря, — неудачу действительно надо заметить сразу.

## Сборка для production

```bash
npm run build          # frontend/dist/index.html
```

Сборка даёт **один файл** — `vite-plugin-singlefile` встраивает JS и CSS прямо в
`index.html`. Поэтому статику можно положить в classpath и отдавать тем же
Spring Boot, без отдельного веб-сервера.

В Docker это делается автоматически: стадия `frontend` собирает интерфейс, затем
`dist` копируется в `src/main/resources/static`, после чего собирается `jar`.
Spring Boot отдаёт `static/index.html` сам — отдельный контроллер для этого не
нужен.

Если фронтенд нужен рядом с backend, но отдельно (например, для разработки), то
`APP_ALLOWED_ORIGINS` должен содержать его адрес.

### Отдельный статический сервер

Если интерфейс всё-таки нужно раздавать отдельно — например, своей CDN-раздачей, —
то статику кладут в nginx, а backend разрешает этот источник:

```bash
APP_ALLOWED_ORIGINS=https://analizer.example.com
COOKIE_SAME_SITE=None
COOKIE_SECURE=true
```

Последние две переменные обязательны: браузер не принимает `SameSite=None` без
`Secure`, и сессия терялась бы на каждом запросе.

## Чего здесь нет

- **Роутинга по URL.** Страницы переключаются состоянием, а не адресом, поэтому
  Spring Boot не нуждается в отдельном fallback для SPA. Если появится настоящий
  маршрутизатор, нужен будет `@{"/**": "forward:/index.html"}` или равнозначное.
- **Тестов.** Интерфейс проверяется сборкой, проверкой типов и ручным прогоном.
  Тесты стоит заводить на `useAutoSync`: там легко ошибиться в порядке запусков, и
  ошибка проявляется уже у пользователя.
- **Линтера.** `npm run typecheck` ловит многое, но не порядок импортов и не
  мёртвый код — для этого понадобится ESLint.
