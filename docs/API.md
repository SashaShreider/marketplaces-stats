## Как устроен API

Три группы методов, различающиеся по побочным эффектам. По префиксу пути сразу видно,
изменит запрос данные или нет.

| Префикс | Что делает | Ходит в API маркетплейса | Тратит квоту |
|---|---|---|---|
| `/imports` | **Команды.** Запускает загрузку данных | **да** | **да** |
| `/data` | Состояние нашей базы: что загружено, что нет | нет | нет |
| `/analytics` | Отчёты, посчитанные по нашей базе | нет | нет |

**Правило, из которого следует всё остальное:** только группа `imports` имеет побочные
эффекты. Методы `data` и `analytics` можно вызывать часто и без риска исчерпать квоту.

**Маркетплейс — сегмент пути `{marketplace}`.** Это идентификатор ресурса, а не деталь
реализации: клиент знает, *что* хочет, а как это добыть — дело адаптера. Добавление
Wildberries не меняет ни одного пути.

```
/api/marketplaces/{marketplace}/imports/finance
/api/marketplaces/{marketplace}/data/coverage
/api/marketplaces/{marketplace}/analytics/daily
```

## Вход и доступ

**Без сессии доступ закрыт.** Любой метод, кроме перечисленных ниже, отвечает
`401`. Отдельной страницы входа сервер не отдаёт и на неё не редиректит: код ответа
достаточен, а какую страницу показать, решает фронтенд.

| Метод | Открыт | Назначение |
|---|---|---|
| `POST /api/auth/register` | да | завести пользователя |
| `POST /api/auth/login` | да | войти и получить куку |
| `GET /api/auth/csrf` | да | получить CSRF-токен |
| `GET /actuator/health` | да | проверка живости |
| `GET /v3/api-docs` | да | машинный контракт API |
| всё остальное | **нет** | требует сессии |

### Машинный контракт

`GET /v3/api-docs` отдаёт весь API в формате OpenAPI 3.1. Он открыт, потому что по нему
генерируются типы до входа — иначе фронтенд пришлось бы собирать вслепую.

```
npx openapi-typescript docs/openapi.json -o frontend/src/api/schema.d.ts
```

Файл `docs/openapi.json` лежит в репозитории и проверяется тестом на расхождение с кодом:
после изменения любого метода его нужно пересобрать, иначе сборка упадёт. Команда
пересборки приведена в [README](../README.md).

Документация, которую вы читаете, объясняет **смысл** — что означает число, когда ноль
бывает обманчивым, почему расходы по товарам меньше дневных. Контракт описывает **форму**
и объяснений не содержит. Для работы клиента нужен контракт, для понимания — этот файл.

### Порядок первого запроса

```
GET  /api/auth/csrf      → кука XSRF-TOKEN и значение токена
POST /api/auth/register  → 201, логин и отображаемое имя
POST /api/auth/login     → 200, кука JSESSIONID
PUT  /api/marketplaces/{mp}/credentials → подключить маркетплейс
POST /api/marketplaces/{mp}/imports/…  → запустить импорт
```

### Если фронтенд запущен отдельно

По умолчанию приложение отвечает только своему источнику, и CORS-заголовков в ответе нет
вообще. Если фронтенд поднят на другом порту, браузер выбросит ответ, и это выглядит как
«сервер молчит» — на деле это запрет на стороне клиента.

Адрес разрешённого источника задаётся переменной `APP_ALLOWED_ORIGINS`:

```
APP_ALLOWED_ORIGINS=http://localhost:5173
```

Два заголовка обязательны и появляются только при заданном списке:
`Access-Control-Allow-Origin` и `Access-Control-Allow-Credentials: true`. Второй нужен,
чтобы браузер приложил куку сессии: без него запрос выглядит анонимным и получает `401`
при заведомо верном пароле.

Предварительный запрос `OPTIONS` проходит **до** проверки CSRF. Если бы порядок был
обратным, `OPTIONS` отклонился бы, браузер не отправил бы сам запрос, а в консоли
лежала бы пустая ошибка сети без кода.

Для публикации по HTTPS задайте `COOKIE_SAME_SITE=None` и `COOKIE_SECURE=true`. С
кукой `SameSite=None` без `Secure` браузер её не примет, а с `Secure` на обычном HTTP —
тоже: сессия будет теряться на каждом запросе.

### `GET /api/auth/csrf`

Формально открыт, но нужен всем остальным: методы, меняющие состояние, требуют заголовок
`X-XSRF-TOKEN`.

```json
{ "headerName": "X-XSRF-TOKEN", "parameterName": "_csrf", "token": "5a203986-af63-4ca9-965e-…" }
```

> Токен лежит в куке `XSRF-TOKEN` **и** в этом ответе. Отправлять нужно и куку, и
> заголовок с тем же значением — именно так работает браузер.

### `POST /api/auth/register`

```json
{ "login": "ivan", "password": "long-password-1", "displayName": "Иван" }
```

| Поле | Обязательное | Правило |
|---|---|---|
| `login` | да | 3–64 символа, без пробелов, уникален |
| `password` | да | минимум 8 символов, хранится BCrypt-хэшем |
| `displayName` | нет | пустое имя подставляется по логину |

Ответ `201`:

```json
{ "login": "ivan", "displayName": "Иван" }
```

Сессия **не** создаётся: первый экран после регистрации — предсказуемая форма входа.

| Код | Когда |
|---|---|
| `201` | пользователь заведён |
| `400` | логин короче 3 символов, длиннее 64, с пробелом; пароль короче 8 |
| `409` | логин уже занят |

> Восстановления пароля нет: почта не запрашивается. Забытый пароль восстанавливается
> только правкой базы.

### `POST /api/auth/login`

```json
{ "login": "ivan", "password": "long-password-1" }
```

Ответ `200` с кукой `JSESSIONID`:

```json
{ "login": "ivan", "displayName": "Иван" }
```

Неверные данные дают `401`, а не `400`, и текст одинаков для «нет такого логина» и
«не тот пароль» — иначе перебор логинов упрощался бы.

### `POST /api/auth/logout`

`204`. Сессия уничтожается, и старая кука `JSESSIONID` перестаёт работать.

### `GET /api/auth/me`

Отдельная проверка входа: `200` с пользователем либо `401`. Фронтенд вызывает его при
старте и решает, показать приложение или форму входа.

```json
{ "login": "ivan", "displayName": "Иван" }
```

### `PUT /api/marketplaces/{mp}/credentials`

Подключение маркетплейса. Отдельный шаг после регистрации, а не её часть: ключи
истекают, менять их приходится, и менять аккаунт для этого не нужно.

```json
{ "clientId": "1154", "apiKey": "…" }
```

| Код | Когда |
|---|---|
| `200` | маркетплейс подключён или реквизиты заменены |
| `400` | маркетплейс отверг ключи — `type: urn:analizer:error:credentials-rejected`, поле `remoteStatus` |
| `404` | неизвестный маркетплейс |

Повторная отправка тех же ключей просто перезаписывает их — метод идемпотентен.

Ответ:

```json
{ "marketplace": "OZON", "clientId": "1154" }
```

> Секретный ключ не возвращается ни здесь, ни в каком-либо другом ответе, и не пишется
> в логи. Проверяется это тестом, а не комментарием.
>
> Перед сохранением ключи проверяются настоящим запросом к маркетплейсу. Иначе
> пользователь узнал бы о неверном ключе через три неудачных импорта.
>
> `TODO(#encrypt-credentials)`: ключ хранится в открытом виде. Утечка дампа базы даёт
> доступ ко всем магазинам; планируется AES-GCM и мастер-ключ в `APP_ENCRYPTION_KEY`.

### `DELETE /api/marketplaces/{mp}`

Удаляет подключение магазина **вместе со всеми его данными**: начислениями, каталогом
товаров, днями и прогонами импорта.

| Код | Когда |
|---|---|
| `204` | магазин удалён, тело пустое |
| `401` | нет сессии |
| `404` | неизвестный маркетплейс |
| `409` | магазин не подключён — `type: urn:analizer:error:not-connected` |

Метод необратим, и это не опечатка в интерфейсе: восстановить можно только повторным
импортом из OZON, то есть заново потратив квоту. Поэтому удаление неподключённого магазина
отклоняется — скорее всего, клиент ошибся адресом, и молчаливый `204` выглядел бы как
успех.

После удаления `GET /api/marketplaces` показывает магазин как неподключённый, и его можно
подключить заново через `PUT …/credentials`. Справочник маркетплейсов и общий справочник
типов начислений не удаляются: они не принадлежат пользователю.

## Правила общие для всех методов

### Идентификатор аккаунта

Аккаунт **не передаётся в запросе**. Он определяется текущим пользователем и
маркетплейсом. На маркетплейс заводится ровно один аккаунт на пользователя —
ограничение в базе, а не в коде.

> Раньше был параметр `?clientId=`. Это идентификатор OZON — у Wildberries он называется
> `companyId`, и выставлять его в общем API значило зашить в контракт одно конкретное
> имя. Теперь аккаунт определяется тем, кто вошёл, и подменить его в запросе негде:
> идентификатора просто нет в параметрах.
>
> Попытка открыть чужой прогон импорта по номеру даёт `404`, а не чужие данные: иначе
> перебором номеров можно было бы увидеть чужой магазин.

### Даты

ISO 8601, формат `ГГГГ-ММ-ДД`. Обе даты включительные: `dateFrom=2026-09-01&dateTo=2026-09-30`
означает 30 дней. `dateTo` раньше `dateFrom` — ошибка `400`.

### Знаки сумм

Суммы хранятся **со знаком, как их отдаёт OZON**: доход положителен, расход отрицателен.
Это делает отчёт сравнимым с личным кабинетом. Там, где клиенту нужен положительный
расход, есть отдельные поля.

Тождество отчёта, проверенное на реальных выгрузках:

```
доходы − расходы = к выплате
```

### Ключи с `null`

Поля со значением `null` **присутствуют в ответе**, а не отсутствуют. Клиент может
рассчитывать, что ключ есть.

### Полные ответы — всегда

Все методы возвращают полный объект, а не только запрошенную часть. Это дороже по
трафику, но позволяет расширять контракт, не ломая клиентов.

## `GET /api/marketplaces`

Какие маркетплейсы доступны и что подключено у текущего пользователя. Единственный
метод без сегмента маркетплейса: он отвечает на вопрос «что вообще доступно», поэтому
вызывается до того, как известен конкретный маркетплейс.

**Параметров нет.** Собственных запросов к маркетплейсам не выполняет.

```json
[
  {
    "code": "OZON",
    "name": "OZON",
    "connected": true,
    "accountName": "OZON 1154",
    "clientId": "1154",
    "catalogProducts": 108,
    "importRuns": 1
  }
]
```

| Ключ | Тип | Пояснение |
|---|---|---|
| `code` | строка | Код маркетплейса. **Подставляйте его в путь следующих запросов** |
| `name` | строка | Отображаемое название |
| `connected` | булево | Задан ли аккаунт. При `false` запуск импорта вернёт `409` с просьбой подключить |
| `accountName` | строка \| null | Название аккаунта. `null`, если аккаунта ещё нет |
| `clientId` | строка \| null | Идентификатор клиента. **Секретного ключа здесь не бывает** |
| `catalogProducts` | число | Товаров в каталоге. `0` означает «каталог не импортировался» |
| `importRuns` | число | Сколько импортов запускалось за всё время |

**Как читать:** `connected: false` — показать форму подключения реквизитов, а не
запускать импорт. `catalogProducts: 0` — предложить импорт каталога.

Список показывает все маркетплейсы системы, а не только подключённые: иначе
пользователь не увидит, что Wildberries вообще поддерживается, и не поймёт, куда идти
подключаться. Различаются они полем `connected`.

> Аккаунты других пользователей в ответе не показываются: это утечка самого факта
> работы магазина. `clientId` и `catalogProducts` всегда относятся к текущему
> пользователю.

## Импорты

Единственная группа с побочными эффектами. Загрузка всегда **фоновая**: POST сразу
возвращает номер прогона, работа продолжается после ответа.

Месяц — десятки обращений к OZON, год — сотни. Если ждать их внутри HTTP-запроса,
клиент отвалится по таймауту, хотя данные наполовину загрузятся.

### `POST /api/marketplaces/{mp}/imports/finance`

Запускает импорт начислений за период.

| Параметр | Обязательный | Пояснение |
|---|---|---|
| `dateFrom` | да | Начало периода включительно |
| `dateTo` | да | Конец периода включительно |
| `refreshAccrualTypes` | нет | Обновить ли справочник типов начислений. Стоит **одного дополнительного** запроса к OZON. По умолчанию `false` |

**Ответ `202 Accepted`:**

```json
{
  "id": 2,
  "marketplace": "OZON",
  "importType": "FINANCE",
  "dateFrom": "2026-09-26",
  "dateTo": "2026-09-26",
  "status": "PENDING",
  "totalUnits": 1,
  "doneUnits": 0,
  "skippedUnits": 0,
  "failedUnits": 0,
  "currentUnit": null,
  "error": null,
  "createdAt": "2026-10-05T04:01:12.408Z",
  "startedAt": "2026-10-05T04:01:12.430Z",
  "finishedAt": null,
  "inProgress": true,
  "percent": 0
}
```

**Что происходит дальше.** Догружаются только недостающие дни. Уже загруженные
окончательные дни повторно не запрашиваются — повторный запуск не создаёт дублей и не
тратит квоту зря.

**Аккаунт создаётся автоматически**, если его ещё нет: на чистой установке первый же
импорт и должен приводить систему в рабочее состояние.

**Может вернуть `409`**, если уже идёт импорт пересекающегося периода — два процесса
писали бы одни и те же операции.

### `POST /api/marketplaces/{mp}/imports/catalog`

Запускает импорт характеристик товаров: названий, ISBN, авторов, обложек.

**Параметров нет.** Периода у каталога нет, поэтому дат в запросе не бывает.

Каталог каждый раз переписывается целиком: OZON не сообщает, какие товары изменились,
а выборочный перебор стоил бы столько же запросов.

**Ответ `202`** — то же, что у финансового импорта, но `importType: "CATALOG"`,
а `dateFrom` и `dateTo` равны `null`.

**Может вернуть `409`** с `conflict: CATALOG_BUSY`: каталог у аккаунта один, поэтому
любая активная загрузка каталога конфликтует с новой. Импорт каталога **не** блокирует
финансовый — у того другая логика конфликта.

### Ответ импорта — `ImportProgress`

Один и тот же объект возвращается при запуске и при опросе прогресса.

| Ключ | Тип | Пояснение |
|---|---|---|
| `id` | число | Номер прогона. Используйте в `GET /imports/{importId}` |
| `marketplace` | строка | Код маркетплейса |
| `importType` | строка | `FINANCE` — начисления, `CATALOG` — товары |
| `dateFrom` | дата \| null | Период финансового импорта. `null` у каталога |
| `dateTo` | дата \| null | Период финансового импорта. `null` у каталога |
| `status` | строка | Состояние прогона, см. ниже |
| `totalUnits` | число | **Единиц работы всего.** Дней у финансового импорта, товаров у каталога |
| `doneUnits` | число | Успешно обработано |
| `skippedUnits` | число | Пропущено как уже загруженное |
| `failedUnits` | число | Не удалось обработать. Такие единицы числятся **неудавшимися, а не пустыми** |
| `currentUnit` | строка \| null | Дата в работе у финансового импорта, SKU — у каталога |
| `error` | строка \| null | Причина неудачи. Заполняется при `status: FAILED` |
| `createdAt` | дата-время | Когда прогон создан |
| `startedAt` | дата-время \| null | Когда началась работа |
| `finishedAt` | дата-время \| null | Когда закончилась |
| `inProgress` | булево | **`true`, пока импорт идёт.** Опрашивайте, пока не станет `false` |
| `percent` | число | Готовность 0–100, считается с учётом пропущенных и упавших |

**Значения `status`:**

| Значение | Что означает | Что делать в UI |
|---|---|---|
| `PENDING` | Создан, работа ещё не началась | Показать ожидание |
| `RUNNING` | Идёт | Полоса прогресса по `percent` |
| `DONE` | Завершён без ошибок | Показать результат |
| `FAILED` | Часть единиц не удалась или прогон упал целиком | Показать `error`, предложить повторить |
| `CANCELLED` | Отменён | Показать как прерванный |

**Прогресс виден по ходу, а не в конце.** `doneUnits` растёт по мере сохранения,
поэтому результат доступен до окончания импорта.

### `GET /api/marketplaces/{mp}/imports`

Последние прогоны, новые сверху. Не более 20.

**Всегда массив**, даже если прогонов ещё не было. Клиенту не нужно различать пустой
список и `null`.

```json
[
  {
    "id": 2,
    "marketplace": "OZON",
    "importType": "FINANCE",
    "dateFrom": "2026-09-26",
    "dateTo": "2026-09-26",
    "status": "DONE",
    "totalUnits": 1,
    "doneUnits": 1,
    "skippedUnits": 0,
    "failedUnits": 0,
    "currentUnit": null,
    "error": null,
    "createdAt": "2026-10-05T04:01:12.408Z",
    "startedAt": "2026-10-05T04:01:12.430Z",
    "finishedAt": "2026-10-05T04:01:13.882Z",
    "inProgress": false,
    "percent": 100
  }
]
```

Фильтра по виду импорта нет: клиенту полезно видеть и финансовые, и импорты каталога

## Состояние данных

### `GET /api/marketplaces/{mp}/data/coverage`

Что загружено, чего не хватает и какие данные ещё не окончательные.

| Параметр | Обязательный | Пояснение |
|---|---|---|
| `dateFrom` | да | Начало периода включительно |
| `dateTo` | да | Конец периода включительно |

> **Про один день.** Чтобы узнать состояние одного дня, передайте одинаковые `dateFrom`
> и `dateTo`. Отдельного метода «про день» нет намеренно: он был бы тем же запросом с
> другим числом параметров.

Отвечает и до первой синхронизации — отсутствие данных это ответ, а не ошибка.

```json
{
  "requestedDays": 30,
  "loadedDays": 0,
  "finalDays": 0,
  "failedDays": 0,
  "missingDays": ["2026-09-01", "2026-09-02", "..."],
  "provisionalDays": [],
  "failedDates": [],
  "sumOfLoadedDays": 0,
  "allFinal": false,
  "complete": false,
  "empty": true,
  "needsSync": true,
  "percentLoaded": 0
}
```

| Ключ | Тип | Пояснение |
|---|---|---|
| `requestedDays` | число | Дней в запрошенном периоде |
| `loadedDays` | число | Дней, по которым начисления загружены |
| `finalDays` | число | Из загруженных — окончательные |
| `failedDays` | число | Дней, которые не удалось загрузить |
| `missingDays` | массив дат | Чего не хватает |
| `provisionalDays` | массив дат | Загружены, но суммы могут измениться |
| `failedDates` | массив дат | Дни с ошибкой |
| `sumOfLoadedDays` | число | Сумма начислений по загруженным дням |
| `allFinal` | булево | Период закрыт и все дни окончательные |
| `complete` | булево | Все дни загружены, ни один не провалился |
| `empty` | булево | Не загружено ни одного дня |
| `needsSync` | булево | **Есть смысл предлагать загрузку** |
| `percentLoaded` | число | Готовность 0–100 |

**Зачем `provisionalDays`.** Начисления за текущий день продолжают приходить в течение
суток, а за вчерашний могут появиться позже — возвраты и корректировки. Такие дни
загружены, но доверять им как окончательным нельзя.

**Зачем `finalDays`.** Окончательным день считается не по дате, а по изменению суммы:
при каждой повторной загрузке сумма сравнивается с предыдущей. Пока сумма меняется,
день не окончательный.

### `GET /api/marketplaces/{mp}/data/catalog`

Состояние каталога товаров. Возвращает **количество и дату последней загрузки**, а не
сами товары — чтобы посмотреть товары вместе с финансами, есть
`/analytics/products`.

```json
{
  "products": 108,
  "lastSyncedAt": "2026-10-05T04:00:38.501167Z",
  "loaded": true
}
```

| Ключ | Тип | Пояснение |
|---|---|---|
| `products` | число | Товаров в каталоге |
| `lastSyncedAt` | дата-время \| null | Когда каталог обновлялся в последний раз |
| `loaded` | булево | `false`, если импорта каталога ещё не было |

> `loaded: false` при `products: 0` означает «каталог ещё ни разу не импортировался»,
> а **не** «у продавца нет товаров».

### `GET /api/marketplaces/{mp}/data/authors`

Варианты авторов для подсказок фильтра.

```json
["Акимова татьяна Викторовна", "А.В. Сурцуков", "Б. И. Жильцов", "Сурцуков А.", "Черняев А. Ю."]
```

Список строится из того, что **реально ввёл продавец**, поэтому может содержать
странные значения: если вместо имени написаны инициалы, подсказка повторит инициалы.
Это честнее, чем предлагать несуществующие написания.

В списке лежат ровно те строки, которые найдут товары, поэтому значение из подсказки
можно **передать в параметр `author` как есть**. Рядом могут стоять «Сурцуков А.»,
«Сурцуков Анатолий» и «А.В. Сурцуков» — это три написания одного человека, и свести
их к одному может только продавец, в карточках товара.

**Верхний уровень:**

| Ключ | Тип | Пояснение |
|---|---|---|
| `marketplace` | строка | Код маркетплейса |
| `dateFrom` / `dateTo` | дата | Период отчёта |
| `status` | строка | См. ниже |
| `coverage` | объект | Покрытие периода, см. ниже |
| `days` | массив | По одному объекту на каждый день периода, включая дни без начислений |
| `income` | число | Доходы за период, положительное число |
| `expenses` | число | Расходы за период, **положительное** число (модуль) |
| `payout` | число | К выплате по данным OZON |
| `total` | объект | Раскладка по статьям, **включая количество за период** |
| `reconciled` | булево | **`income − expenses = payout` по каждому дню** |
| `final` | булево | Все дни окончательные, можно печатать как итог |

> **Где искать количество за период.** Только в `total.soldQuantity` и
> `total.returnedQuantity` — на верхнем уровне их нет, в отличие от денег. Это известная
> непоследовательность формы ответа, помечена `TODO(#response-duplication)` в коде.
> Суммировать `days[].soldQuantity` не нужно: результат тот же, а лишний проход по
> массиву.

**Значения `status`:**

| Значение | Что означает | Что делать в UI |
|---|---|---|
| `READY` | Все дни загружены, ошибок нет | Показывать цифры как есть |
| `PARTIAL` | Часть дней загружена, часть — нет | Плашка «показаны неполные данные» + кнопка догрузки |
| `NOT_LOADED` | Ни один день не загружен | Плашка «данных нет» + кнопка загрузки |
| `HAS_ERRORS` | Хотя бы один день не удалось загрузить | Плашка с ошибкой + кнопка повтора |

**`coverage` в отчёте** содержит те же поля, что и `/data/coverage`, плюс:

| Ключ | Пояснение |
|---|---|
| `fullyFinal` | Все дни загружены и окончательные |
| `suitableForProfit` | Можно ли считать прибыль по этим данным |

**`days[].breakdown`** — раскладка со знаками, как в OZON:

| Ключ | Что это |
|---|---|
| `sales` | Цена продаж |
| `returns` | Возвраты. Отрицательное число, уменьшает доход |
| `partnerProgramme` | Начисления по программе партнёров: бонусы и ковейст. **Это доход** |
| `commission` | Комиссия маркетплейса. При возврате положительна: комиссия возвращается |
| `logistics` | Логистика |
| `otherExpenses` | Прочие списания: ITEM, NON_ITEM, CONTAINER |

**Количество в строке дня:**

| Ключ | Что это |
|---|---|
| `soldQuantity` | Единиц продано. Возвраты сюда **не входят** |
| `returnedQuantity` | Единиц возвращено |

Два отдельных числа, а не одно. `soldQuantity` уменьшать на `returnedQuantity` не нужно —
сложение покажет чистую цифру, а молча уменьшенное число читалось бы как «продали N», хотя
на самом деле продали N плюс ещё несколько и часть вернули.

Что **не** попадает в количество: строки начислений, у которых OZON не прислал
`sale_price`. Это удержания и штрафы за доставку, они приходят с `quantity`, равным
единице, но продажами не являются. Включение дало бы завышение примерно на двадцать
процентов — на реальных данных сентября 2026 это 119 единиц против 555 настоящих продаж.

**`days[].expensesByType`** — детализация расходов по типам начислений:

| Ключ | Что это |
|---|---|
| `typeId` | Идентификатор типа в OZON. Устойчив к переименованию, но нечитаем |
| `name` | Служебное название из справочника: `PayPerClick`, `StarsMembership` |
| `description` | Человеческое описание из того же справочника: «Оплата за клик». **Показывайте его** |
| `amount` | Сумма с отрицательным знаком |

Показывать пользователю следует `description`: `PayPerClick` продавец не поймёт, а «Оплата за клик» поймёт. `name` оставлено для случаев, когда описание пустое.

Справочник типов открыт и пополняется, поэтому опирайтесь на `name` и `description`, а не на `typeId`. Тип, которого в справочнике нет, придёт с именем `Тип 12345` и пустым описанием — это честнее, чем потерять расход молча.

## Четыре вещи, которые часто понимают неправильно

### 1. Ноль бывает разным

**В дневном отчёте** ноль за незагруженный день — это ложь, поэтому день помечается
как незагруженный.

**В отчёте по товарам** ноль у товара, который есть в каталоге, — правда: товар
существует, продаж за период не было. Молчать о нём означало бы скрыть товары, которые
перестали продаваться.

Но если период загружен не полностью, это указано в `status` и `coverage`, и нулям
верить нельзя.

### 2. Расходы по товарам меньше дневных

Расходы типов `NON_ITEM` и `CONTAINER` приходят от OZON **без привязки к SKU**.
Распределить их между товарами можно было бы только выдумав правило, поэтому этого не
происходит, а сумма показана отдельным полем:

```
unallocatedExpenses = 3353.58
totals.expenses     = 13308.45
                       ─────────
                       16662.03  ← столько расходов в дневном отчёте
```

Отсюда **правильная сверка**, а не `income − expenses = payout`:

```
income − expenses − payout = unallocatedExpenses
25280.00 − 13308.45 − 8617.97 = 3353.58 ✓
```

### 3. Фильтр по автору строгий

Ищется ровно то, что введено, — так, как автор назван в карточке товара. Имена у OZON
приходят в разных форматах, и «Сурцуков А.», «Сурцуков Анатолий», «А.В. Сурцуков» и
«Анатолий Васильевич Сурцуков» — это четыре написания одного человека, но фильтр
различает их:

| Запрос | Результат |
|---|---|
| `author=Сурцуков Анатолий` | только товары с таким именем в карточке |
| `author=Сурцуков А.` | только товары с такой формой — другой набор |
| `author=Сурцуков` | ничего: такой строки нет ни в одной карточке |

Регистр значения тоже значения не имеет: `асилий Калязин` найдёт товар, а
`Асилий Калязин` — нет. В выгрузке действительно есть товар с именем, набранным с
маленькой буквы.

**Исключение одно: перечисленные авторы.** Если в карточке их несколько, то подходит
любой из перечисленных. «Черняев А. Ю., Ланде А. А.» разбирается на два значения, и
`author=Ланде А. А.` находит тот же товар, что и `author=Черняев А. Ю.` — искать надо
одно из имён, а не всю строку целиком.

Почему так строго: сведение имён к «фамилия + инициалы» угадывает. Оно склеило бы
разные написания одного человека, но не различило бы «Герланец Валерий» и
«Герланец Валерий Петрович», а людей с общей фамилией склеило бы в одного. В отчёте о
продажах лишний товар — это лишние деньги, поэтому точность важнее удобства.
Унифицировать написание может продавец — в карточках своего кабинета.

### 4. Количество продаж — не всё, у чего есть `quantity`

В начислениях OZON есть строки, у которых количество равно единице, продажей они не
являются, и в счёт не попадают. Это удержания и штрафы за доставку: у них `commission`
равен `null`, поэтому цена продажи неизвестна, а сама операция целиком отрицательная и
равна логистике.

На настоящих данных за апрель и сентябрь 2026 таких строк 139 при 555 настоящих
продажах. Наивное суммирование `quantity` завысило бы количество на 21 процент, и
заметить это можно было бы только ручной сверкой с кабинетом.

Ещё одна ловушка рядом: при `quantity > 1` поле `sale_price` приходит **за всю
позицию**, а не за штуку, и `seller_price` — уже **за единицу**. Делить выручку на
количество нельзя.

## Ошибки

Формат **RFC 7807** (`application/problem+json`) у всех ошибок.

```json
{
  "type": "urn:analizer:error:unknown-marketplace",
  "title": "Неизвестный маркетплейс",
  "status": 404,
  "detail": "Неизвестный маркетплейс: WB. Доступные: GET /api/marketplaces",
  "instance": "/api/marketplaces/wb/imports",
  "marketplace": "WB"
}
```

| Код | Когда | Дополнительные поля |
|---|---|---|
| `400` | Неверные параметры: нет обязательного, `dateTo` раньше `dateFrom` | — |
| `400` | Маркетплейс отверг реквизиты | `remoteStatus` |
| `401` | Нет сессии, либо неверный логин или пароль | — |
| `403` | Запрос без действующего CSRF-токена | — |
| `404` | Неизвестный маркетплейс | `marketplace` |
| `404` | Несуществующий прогон импорта | — |
| `409` | Импорт уже идёт | `conflict`, `activeImportId`, `activeImport`, `requestedFrom`, `requestedTo` |
| `409` | Маркетплейс не подключён | — |
| `409` | Логин уже занят | — |
| `502` | API маркетплейса вернул ошибку | `ozonStatus`, `ozonCode` |

> `401` и `403` в теле ответа не различают «сессии нет» и «токен не тот»: пока пользователь
> анонимен, отказ в доступе отвечает кодом входа, а не запретом. Клиенту достаточно
> знать, что нужно войти заново.

### Значения `conflict`

| Значение | Что произошло | Что делать |
|---|---|---|
| `OVERLAPPING_PERIOD` | Идёт импорт пересекающегося периода | Дождаться `activeImportId` |
| `CATALOG_BUSY` | Идёт импорт каталога | Дождаться `activeImportId` |
| `MARKETPLACE_NOT_CONNECTED` | `DELETE` магазина, который не подключён | Проверить `connected` в `GET /api/marketplaces` |

Значения `MARKETPLACE_NOT_CONNECTED` и `LOGIN_TAKEN` живут в поле `type` ответа, а не в
`conflict`: последнее поле есть только у конфликтов импорта, где клиенту нужно знать, что
именно дождаться.

Пример:

```json
{
  "type": "urn:analizer:error:import-conflict",
  "title": "Импорт пересекающегося периода уже выполняется",
  "status": 409,
  "detail": "Импорт уже выполняется: прогон №2 за период 2026-09-01 — 2026-09-30. Дождитесь его окончания: повторный импорт пересекающегося периода запрещён, иначе два процесса писали бы одни и те же операции.",
  "instance": "/api/marketplaces/ozon/imports/finance",
  "conflict": "OVERLAPPING_PERIOD",
  "activeImportId": 2,
  "activeImport": "прогон №2 за период 2026-09-01 — 2026-09-30",
  "requestedFrom": "2026-09-01",
  "requestedTo": "2026-09-30"
}
```

**Не является ошибкой.** Отчёт за период, который не загружался, возвращает `200` со
статусом `NOT_LOADED`. Отсутствие данных — это состояние, а не сбой: вернув ошибку,
пришлось бы заставлять клиента угадывать, что произошло.

## Сценарии

### Первый запуск

```http
GET  /api/auth/csrf
POST /api/auth/register                       → 201
POST /api/auth/login                          → 200 и кука сессии
PUT  /api/marketplaces/ozon/credentials       → 200, ключи проверены и сохранены
GET  /api/marketplaces                        → видно, что OZON подключён
POST /api/marketplaces/ozon/imports/catalog
GET  /api/marketplaces/ozon/imports/{id}          до inProgress = false
POST /api/marketplaces/ozon/imports/finance?dateFrom=…&dateTo=…
GET  /api/marketplaces/ozon/imports/{id}          до inProgress = false
GET  /api/marketplaces/ozon/analytics/products?dateFrom=…&dateTo=…
```

### Догрузить период

```http
GET  /api/marketplaces/ozon/data/coverage?dateFrom=…&dateTo=…
     → смотрим needsSync и missingDays
POST /api/marketplaces/ozon/imports/finance?dateFrom=…&dateTo=…
GET  /api/marketplaces/ozon/imports/{id}          до inProgress = false
```

Загружаются только недостающие дни. Уже загруженные окончательные не трогаются.

### Отчёт с фильтром по автору

Значение `author` берётся из подсказок — тогда оно гарантированно что-то найдёт.
Регистр и написание сохраняются как есть.

```http
GET /api/marketplaces/ozon/data/authors           подсказки
GET /api/marketplaces/ozon/analytics/products?dateFrom=…&dateTo=…&author=Сурцуков%20А.
```

### Сверка с кабинетом OZON

```http
GET /api/marketplaces/ozon/analytics/daily?dateFrom=…&dateTo=…
     → reconciled = true  значит income − expenses = payout
     → total.sales, total.commission и прочие можно сверить построчно
```

### Бюджет запросов к OZON

| Действие | Запросов |
|---|---|
| Импорт каталога | **1** (108 товаров одним ответом) |
| Один день начислений | 1–2 |
| `refreshAccrualTypes=true` | +1 |
| Месяц начислений | 30+ |
| Любой метод `/data` и `/analytics` | **0** |

Первый прогон делайте как «каталог + один день» — этого хватает, чтобы увидеть всё.

## Ограничения

**Один аккаунт на маркетплейс у пользователя.** Два аккаунта одного пользователя на одном
маркетплейсе не заведутся — ограничение в базе. Двум разным пользователям с одинаковым
`clientId` это не мешает: `clientId` — понятие OZON, а не наше, и он не обязан быть
уникальным глобально.

Это осознанный компромисс: молча выбрать один аккаунт значило бы отдать данные не того
продавца.

**Защита от параллельных импортов работает в пределах одного процесса.** При нескольких
экземплярах приложения блокировку нужно перенести в базу.

**Период импорта ограничен `2022-01-01`.** OZON не отдаёт более ранние начисления.
