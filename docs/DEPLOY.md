# Публикация проекта на сервер и работа с ним

Полная инструкция: как вести репозиторий, что должно проверяться само, как
арендовать сервер и купить домен, как развернуть проект и как сделать так, чтобы
сайт обновлялся сам после каждого изменения в `main`.

Темы, которые стоит изучить отдельно, помечены 🔍 и собраны в
[конце документа](#темы-для-отдельного-изучения).

---

## 1. Что получится в итоге

```
        Вы пишете код локально
                  │
                  ▼
     ветка задачи feat/… → pull request в dev
                  │
        ┌─────────▼──────────┐
        │  GitHub Actions CI │  тесты backend, типы и сборка frontend,
        │  (ci.yml)          │  сверка контракта API, полный прогон
        └─────────┬──────────┘
                  │ все проверки зелёные → можно вливать
                  ▼
              dev  — здесь живёт разработка, сайт не обновляется
                  │
                  ▼  релиз: pull request dev → main
              main (защищена)
                  │ коммит попал в main
                  ▼
        ┌─────────▼──────────┐
        │ GitHub Actions     │  подключается к серверу по SSH,
        │ (deploy.yml)       │  забирает код, пересобирает контейнер
        └─────────┬──────────┘  и ждёт ответа /actuator/health
                  ▼
              Сервер
     ┌────────────┼────────────┐
     ▼            ▼            ▼
   nginx/Caddy  приложение   PostgreSQL
   :443 TLS     :8080        :5432 (внутри)
   только это   интерфейс    том analizer-pgdata
   наружу       и API
```

Что видит пользователь: открывает `https://ваш-домен` и получает работающий сервис.
Что происходит после `git push` в `main`: через несколько минут сайт уже обновлён.

**Почему так, а не иначе**

Приложение отдаёт и интерфейс, и API с одного порта, поэтому в схеме один контейнер
с кодом, а не «бэкенд плюс отдельный фронтенд». Наружу торчит только обратный прокси
с сертификатом: приложение слушает 8080 внутри и не выходит в интернет сам. Такая
схема объясняет всё остальное — почему приложению не нужен CORS, почему кукам
обязателен HTTPS и почему порт БД закрыт.

## 2. Что нужно знать о проекте перед развёртыванием

| | |
|---|---|
| Backend | Java 21, Spring Boot 4.1, Gradle |
| Frontend | React 19, Vite 7, Tailwind 4, Node 22 |
| База | PostgreSQL 17 |
| Сборка | один Docker-образ: стадия Node собирает интерфейс, стадия JDK собирает `jar`, в образ попадает статика |
| Образ | ~712 МБ |
| Портов наружу | 443 (прокси) — всё остальное закрыто |
| Схема БД | версии Flyway в `src/main/resources/db/migration`, применяются сами при старте |
| Тесты | полный прогон 8–12 минут, `-Pfast` (без БД) — секунды |

Три особенности, которые определяют почти все решения ниже.

**Ключи OZON хранятся в базе открытым текстом.** Пользователь вводит их через
интерфейс, они лежат в таблице аккаунтов продавца. Запланировано шифрование
(`TODO(#encrypt-credentials)`), но его нет. Отсюда: арендовать сервер, где база
под вашим полным контролем, и не отдавать доступ к ней никому постороннему —
в том числе не использовать платформы, где дают веб-доступ к базе из панели.

**Сессия хранится в куке.** Значит для публикации по HTTPS обязательны
`COOKIE_SAME_SITE=None` и `COOKIE_SECURE=true`: браузер не принимает куку
`SameSite=None` без флага `Secure`, и иначе каждый запрос после входа давал бы 401.

**Приложение само обновляет базу при старте.** Отдельного шага «применить миграции»
нет, и это же означает, что откат кода не откатывает миграции. Об этом отдельно в
[разделе 11](#11-откат).

## 3. Как вести репозиторий

### 3.1. Три вида веток

| Ветка | Откуда | Куда | Правило |
|---|---|---|---|
| `main` | — | сервер | Только проверенный код. Каждый коммит здесь публикуется на сайт. |
| `dev` | `main` | `main` через PR | Основная ветка разработки. Сюда сливаются задачи, отсюда уходит релиз. |
| `feat/<что делаем>` | `dev` | `dev` через PR | Ветка задачи. Живёт недолго, потом удаляется. |
| `fix/<что чиним>` | `dev` | `dev` через PR | То же для срочных правок. |

Схема такая: работа идёт в `dev`, релиз — pull request `dev → main`. Публикуется
ровно то, что попало в `main`, а `dev` может содержать незаконченное: на сервер
оно не попадёт, потому что деплой настроен только на `main`.

Две причины, по которым `dev` здесь полезна:

- **На сайте всегда рабочая версия.** `main` обновляется только через проверки, а
  неудачный коммит можно откатить одним движением, не разбираясь, что сломалось.
- **Несколько задач параллельно.** Ветки задач отходят от `dev`, а не от `main`:
  релиз не придётся пересобирать, когда в него сливается одна из них.

Защита `main` обязательна: без неё в неё можно запушить напрямую, и тогда уедет в
прод код, который даже не проходил тесты. Для `dev` защита не нужна — из неё сайт не
разворачивается.

### 3.2. Цикл работы

```bash
git switch dev
git pull                        # свежий dev перед началом задачи
git switch -c feat/author-filter

# … работа, коммиты небольшими осмысленными частями …

git push -u origin feat/author-filter
```

Дальше в GitHub: **Pull requests → New pull request**, base — `dev`. В описании — что
сделано и зачем. Проверки CI запустятся сами.

```bash
gh pr create --base dev --fill     # то же самое из командной строки
```

После зелёных проверок: **Merge pull request** (merge commit — так история сохраняет
понятную структуру «ветка задачи → dev»).

```bash
git switch dev
git pull
git branch -d feat/author-filter        # локальная ветка больше не нужна
git push origin --delete feat/author-filter
```

### 3.2.1. Релиз: `dev` → `main`

Оформленную и проверенную часть `dev` отправляем в `main`:

1. Открыть **Pull requests → New pull request**, `base: main`, `compare: dev`.
2. Дождаться зелёных проверок — они прогонятся повторно.
3. **Merge pull request.**

После этого сработает деплой и сайт обновится сам.

Полезно держать `dev` всегда готовым к релизу: тогда публикация — одна кнопка.
Если в `dev` лежит несколько несвязанных задач, это нормально, но состав PR стоит
писать в описании: что именно уходит на сервер.

🔍 **GitHub CLI (`gh`)** — стоит поставить: из него делаются PR, видятся статусы
проверок и релизы прямо из терминала.

### 3.3. Защита веток

Пока ветка не защищена, в неё можно запушить напрямую — и тогда уедет в прод код,
который даже не проходил тесты.

**`main`** — правило настраивается обязательно:

**Settings → Branches → Add rule → Branch name pattern `main`**:

- ✅ Require a pull request before merging
- ✅ Require status checks to pass — выбрать `CI / Тесты backend`,
  `CI / Проверки frontend`, `CI / Контракт API совпадает с живым`
- ✅ Require branches to be up to date
- ❌ **Не включать** «Require signed commits» и «Require conversation resolution»,
  пока это не понадобится по делу: они только тормозят.

**`dev`** — правило помягче: сайт с неё не разворачивается, но пустить в неё чужой
код всё равно не стоит.

**Branch name pattern `dev`**:

- ✅ Require a pull request before merging
- ✅ Require status checks to pass — те же четыре проверки
- ❌ Require branches to be up to date — можно выключить: без этого задачи сливаются
  свободно, и конфликты решаются уже в `dev`, а не в релизной ветке

Там же: **Settings → Actions → General → Workflow permissions → Read repository
contents permissions**. Для `deploy.yml` этого достаточно: он забирает код на
сервере, а не с токена.

> Деплой настроен только на `main`: коммит в `dev` сайт не обновляет. Это не
> oversight — так и должно быть: публикуется ровно проверенный релиз.

### 3.4. Что не должно попадать в git

Уже настроено в `.gitignore`: `.env`, ключи, `node_modules`, `build`, `dist`,
`.playwright-mcp`, `opencode.jsonc`. Проверьте перед первым коммитом в новой среде:

```bash
git status --short
git check-ignore -v .env
```

Если секрет всё-таки попал в историю, простого удаления из последнего коммита мало —
см. 🔍 **[Отзыв секретов, попавших в git](#секреты-в-репозитории)**.

## 4. Что проверяется перед публикацией

### 4.1. Локально перед `git push`

```bash
.\gradlew.bat test -Pfast        # Linux/macOS: ./gradlew test -Pfast
cd frontend && npm run typecheck && cd ..
```

Полный прогон (`./gradlew test`) нужен перед тем, как трогать что-то крупное: он
поднимает Testcontainers и идёт 8–12 минут.

### 4.2. Автоматически в GitHub

Файл `.github/workflows/ci.yml` уже добавлен в проект и делает четыре проверки:

| Проверка | Что ломает | Сколько идёт |
|---|---|---|
| Модульные тесты backend | логику домена | секунды |
| Контракт API | расхождение `docs/openapi.json` с живым API | ~минута |
| Типы и сборка frontend | несовместимое изменение типов | ~минута |
| Полный прогон с интеграционными тестами | запросы, Flyway, БД | ~10 минут |

Контракт проверяется отдельно, потому что фронтенд должен знать те же типы, что
отдаёт сервер. Расхождение ловится на PR, а не при сборке образа.

Если изменили метод API, пересоберите контракт **до** коммита:

```bash
.\gradlew.bat test --tests=ru.analizer.contract.OpenApiContractIT -Panalizer.updateOpenApi=true
```

### 4.3. Локальная разработка: два адреса, и только один из них с горячими изменениями

Это стоит понять до первого коммита, иначе будет казаться, что проект приходится
перезапускать после каждой правки интерфейса.

| Адрес | Что отдаётся | Правки интерфейса видны сразу |
|---|---|---|
| http://localhost:5173 | Dev-сервер Vite: исходники подгружаются по мере сохранения | **Да** |
| http://localhost:8080 | Статика, собранная при последнем `docker compose up --build` и запечатанная в образ | Нет |

`docker compose up --build` пересобирает образ целиком, поэтому правка `.tsx` в него
не попадает и видна только после пересборки. Для разработки это лишнее: образ нужен,
чтобы убедиться, что production-сборка живая, а не чтобы смотреть на интерфейс.

Рабочий режим на каждый день:

```bash
# 1. один раз в .env — разрешить источник фронтенда
#    APP_ALLOWED_ORIGINS=http://localhost:5173

# 2. база и backend в Docker: БЕЗ --build
docker compose up -d app postgres

# 3. интерфейс с горячей перезагрузкой
cd frontend && npm run dev
```

Дальше работа идёт в браузере на **http://localhost:5173**. Сохранили файл — страница
обновилась сама.

`--build` нужен в двух случаях: захотелось проверить production-сборку в Docker и
после изменения `Dockerfile`, `.dockerignore`, `frontend/package.json` или
`vite.config.ts` — то есть когда меняется то, **как** собирается проект, а не что в
нём написано.

### 4.4. То же самое одной кнопкой в VS Code

Обе команды выше описаны готовыми конфигурациями. Открываете **Run and Debug**
(`Ctrl+Shift+D`), выбираете в списке, жмёте ▶ или `F5`:

| Конфигурация | Что делает |
|---|---|
| `Всё сразу: БД, backend и интерфейс` | `docker compose up -d app postgres` и `npm run dev` — весь рабочий день одной кнопкой |
| `БД и backend с пересборкой образа` | То же с `--build` |
| `Логи backend` | `docker compose logs -f app` — следить за стартом и ошибками |
| `Остановить контейнеры` | `docker compose down`; данные в томе остаются |

Все задачи доступны и через **Terminal → Run Task…** (`Ctrl+Shift+B` — основная).
Разница в том, что панель Run and Debug показывает только `launch.json`, а задачи
из `tasks.json` видны через меню Terminal; набор команд один и тот же.

Оба файла лежат в репозитории, поэтому на новой машине ничего настраивать не нужно.
Личные настройки редактора (`.vscode/settings.json`) в git не попадают — у каждого
свои.

Если правки перестали применяться, проверьте по порядку:

1. Вкладка открыта на 5173, а не на 8080.
2. Dev-сервер вообще жив: `curl http://localhost:5173` отвечает 200.
3. Порт 5173 не занят старым процессом, который держит конфигурацию на момент своего
   старта и не знает про новые файлы:

```powershell
Get-NetTCPConnection -LocalPort 5173 -State Listen |
  Select-Object -ExpandProperty OwningProcess | Stop-Process -Force
cd frontend; npm run dev
```

Третий пункт особенно нужен после переноса или переименования файлов.

## 5. Аренда сервера

### 5.1. Что нужно

| Параметр | Минимум | Рекомендую | Почему |
|---|---|---|---|
| vCPU | 1 | 2 | Сборка образа на сервере идёт параллельно в несколько стадий |
| RAM | 2 ГБ | 2–4 ГБ | JVM + PostgreSQL + сборка Gradle; мало — сборка упадёт по памяти |
| Диск | 20 ГБ | 30–40 ГБ | Образ 712 МБ, кэш Gradle, база, логи |
| Трафик | 100 ГБ | 300 ГБ | Сайт текстовый, но образ тянется при каждом деплое |

Регион выбирайте близко к себе: деплой тянет образ, а скорость зависит от маршрута.

### 5.2. Какой тип хостинга

Для этого проекта — **виртуальный сервер (VPS) с собственным диском**. Не
управляемый хостинг с кнопкой «создать базу»: он потребует отдать доступ к БД
сторонней панели, а в базе лежат ключи OZON.

Ориентиры по провайдерам: Hetzner, DigitalOcean, Vultr, Selectel, Timeweb, Reg.Ru.
Минимальная конфигурация обычно укладывается в сумму, которую можно позволить себе
как расход на подписку.

🔍 **[Аренда VPS и выбор провайдера](#выбор-провайдера-vps)** — разбирается подробнее
ниже.

### 5.3. После покупки

Панель управления выдаст IP, логин (обычно `root`) и пароль **или** SSH-ключ.
Смените пароль при первом входе и включите вход по ключу, отключив пароли:

```bash
ssh root@IP_АДРЕС
passwd                                   # сменить пароль
```

Дальше — по шагам [раздела 8](#8-подготовка-сервера).

## 6. Домен и DNS

Домен покупается отдельно от сервера и не обязан быть в одном месте: хостинг сайта и
регистратор домена могут быть разными провайдерами.

1. Выберите домен и зарегистрируйте его.
2. В панели управления доменом откройте DNS и добавьте записи:

| Тип | Имя | Значение | Зачем |
|---|---|---|---|
| `A` | `@` | IP-адрес сервера | `https://домен` |
| `A` | `www` | IP-адрес сервера | `https://www.домен` |
| `AAAA` | `@` | IPv6, если есть | То же для IPv6 |

3. Распространение занимает от нескольких минут до суток. Проверьте, что домен
   отвечает, ещё **до** настройки сертификата:

```bash
nslookup ваш-домен
ping ваш-домен
```

🔍 **[Регистрация домена и управление DNS](#домен-и-dns)** — как выбрать зону,
сверить регистратора и DNS-провайдера, что делать с конфликтом «домен зарегистрирован,
но не делегирован».

## 7. Секреты

### 7.1. Где что лежит

| Секрет | Где хранится | Комментарий |
|---|---|---|
| Пароль БД | `.env` на сервере | В git не попадает: `.env` в `.gitignore` |
| Ключ SSH для деплоя | GitHub → Secrets | Только там, файл не хранится в репозитории |
| Адрес, пользователь, путь сервера | GitHub → Secrets | Не секрет, но удобно хранить рядом |
| Ключи OZON продавца | Таблица аккаунтов в БД | Вводятся пользователем через интерфейс; **открытым текстом** |

### 7.2. `.env` на сервере

Файл создаётся вручную один раз и **никогда не редактируется из репозитория**:

```bash
cd /srv/analizer
nano .env
```

```bash
# Внутри сети compose имя сервиса, а не localhost: порт 5433 на хосте внутри
# контейнера другой и не существует.
DB_URL=jdbc:postgresql://postgres:5432/analizer
DB_USERNAME=analizer
DB_PASSWORD=<сложный пароль>

# HTTPS настроен, поэтому сессионной куке нужны эти два значения.
COOKIE_SAME_SITE=None
COOKIE_SECURE=true

# Пусто: интерфейс и API отдаются с одного источника, CORS не нужен.
# Заполнять нужно, только если фронтенд живёт на другом домене или порту.
# Например, http://localhost:5173 — если на сервере фронтенд запускается отдельно.
APP_ALLOWED_ORIGINS=

# Реквизиты OZON пользователь вводит сам через интерфейс.
# Здесь их быть не должно.
```

Права на файл: `chmod 600 .env` — читать должен только владелец.

### 7.3. Секреты GitHub

**Settings → Secrets and variables → Actions → New repository secret**:

| Имя | Значение |
|---|---|
| `DEPLOY_HOST` | IP или домен сервера |
| `DEPLOY_PORT` | `22` |
| `DEPLOY_USER` | имя пользователя для деплоя, например `deploy` |
| `DEPLOY_SSH_KEY` | приватный ключ, одна строка, с `\n` вместо переносов |
| `DEPLOY_PATH` | путь на сервере, например `/srv/analizer` |

Секреты **зашифрованы в GitHub** и не показываются в списке после сохранения: если
забудете значение, его придётся перезаписать, а не посмотреть.

### 7.4. Правила, которые здесь важны

- Секрет, попавший в git, **считается скомпрометированным**: его надо не удалять из
  коммита, а заменить. Удаление из последнего коммита ничего не даёт — секрет остаётся
  в истории.
- Ключи OZON лежат в базе открытым текстом. Утечка дампа базы означает утечку всех
  аккаунтов продавцов. Отсюда: база не должна быть доступна из интернета (порт 5432
  закрыт брандмауэром) и бэкапы должны храниться отдельно.
- Не передавайте секреты через аргументы командной строки: они попадают в историю
  shell и в список процессов. Только `.env` и переменные окружения.

🔍 **[Секреты, которые уже утёкли](#секреты-в-репозитории)** — как отозвать пароль БД,
ключ SSH и ключ OZON после попадания в историю.

## 8. Подготовка сервера

Все команды выполняются на сервере после `ssh root@IP`.

### 8.1. Установить Docker

Для Ubuntu/Debian — официальный репозиторий Docker (🔍 **[Установка Docker и Docker
Compose](#установка-docker)**):

```bash
# удаление старых версий, если они были
apt remove docker docker-engine docker.io containerd runc || true

apt update
apt install -y ca-certificates curl
install -m 0755 -d /etc/apt/keyrings
```

Открыты должны быть ровно два порта, и оба — входящие:

> Внимание: если включить `ufw` и забыть `ufw allow OpenSSH`, доступ по SSH

### 8.5.1. Swap для сборки образа на сервере

**Пока образ собирается на сервере, swap не опция, а условие работоспособности.**

Сборка образа (Gradle + Node) на пике берёт 2–4 ГБ. На сервере с 2 ГБ RAM это
ровно тот объём, при котором OOM-killer убивает сборку на самом интересном месте,
и деплой падает без внятной причины: в логах Gradle обрывается на середине, а в
`dmesg` — `Out of memory: Killed process`.

Swap решает именно это: на нём сборка живёт медленнее, но не умирает. На
постоянной основе приложение в нём не нуждается — там всего около 900 МБ.

```bash
# 2 ГБ файла подкачки
fallocate -l 2G /swapfile
chmod 600 /swapfile
mkswap /swapfile
swapon /swapfile

# чтобы пережил перезагрузку
echo '/swapfile none swap sw 0 0' >> /etc/fstab

free -h          # Swap: 2.0Gi
```

Заодно стоит ограничить аппетитивность сборки ядру: без `vm.swappiness` ядро может
 держать страницы в оперативной памяти вместо подкачки, и тогда при нехватке памяти
приложение выбьется первым.

```bash
echo 'vm.swappiness=10' >> /etc/sysctl.conf && sysctl -p
```

Сборку имеет смысл ограничить по параллелизму — на одном ядре она всё равно идёт
последовательно, а Gradle и npm по умолчанию запускают задачи по числу ядер:

```bash
# одна опция на весь деплой, без правок Dockerfile
export DOCKER_BUILDKIT=1
docker compose build --parallel=false app
```

Когда сборка переедет в CI — см. [10.2](#102-автоматический-деплой) — swap можно
уменьшить или убрать: пиков по памяти на сервере больше не будет.

## 9. HTTPS

Сертификат нужен по двум причинам: браузеры требуют HTTPS для нормальной работы
(иначе «небезопасное соединение»), и без него нельзя включить `COOKIE_SECURE`,
а без него не будет работать сессия.

Проще всего **Caddy**: он сам выпускает и сам продлевает бесплатный сертификат
Let's Encrypt. Настройка — три строки:

```bash
apt install -y caddy
nano /etc/caddy/Caddyfile
```

```caddy
ваш-домен, www.ваш-домен {
    reverse_proxy 127.0.0.1:8080
}
```

```bash
systemctl reload caddy
```

Через минуту на `https://ваш-домен` отвечает приложение. Домен должен уже
разрешаться в этот IP — иначе Caddy не сможет получить сертификат и будет
перезапускаться с ошибкой.

Больше ничего настраивать не нужно: прокси передаёт заголовки, приложение работает
за `127.0.0.1` и не знает, что снаружи есть прокси. Формулировки «HTTPS-терминация»
в проекте нет.

🔍 **[Caddy против nginx](#caddy-или-nginx)** — когда стоит выбрать nginx, что такое
сертификаты и как они продлеваются.

> Если выбран nginx, нужно ещё проксировать заголовки `X-Forwarded-*` и настроить
> размер тела запроса для импорта. Пример конфигурации — ниже.

### Если вместо Caddy выбран nginx {#если-вместо-caddy-выбран-nginx}

Caddy сам выпускает и продлевает сертификат, поэтому в нём настройка заканчивается
одной строкой `reverse_proxy`. С nginx сертификат выпускается отдельно — удобнее
всё равно тем, кто уже умеет работать с ним.

```bash
apt install -y nginx certbot python3-certbot-nginx
certbot --nginx -d ваш-домен -d www.ваш-домен
```

```nginx
server {
    server_name ваш-домен www.ваш-домен;

    # Запросы большие не бывают, но прокси не должен обрывать их на 1 МБ по умолчанию.
    client_max_body_size 8m;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

Certbot сам добавил блок для переадресации на HTTPS и обновляет сертификат по
cron. Обновление сертификата без перезагрузки уже описано в его файле `deploy-hook`.

## 10. Публикация

### 10.1. Первый деплой вручную

Делается один раз руками, чтобы понять, что всё живое, до того как это будет делать
робот.

```bash
# на сервере
cd /srv/analizer

# .env уже создан по разделу 7.2
docker compose up -d --build app postgres

# смотреть, пока поднимается
docker compose logs -f app
```

Признак, что всё поднялось:

```bash
curl -fsS http://127.0.0.1:8080/actuator/health    # {"status":"UP"}
curl -I http://127.0.0.1:8080/                      # 200, HTML интерфейса
```

Открыть `https://ваш-домен`, зарегистрироваться, подключить маркетплейс.

> На сервере поднимается только `app` и `postgres`. `pgadmin` — инструмент для
> локальной работы, в интернет его выставлять не нужно: админка базы на публичном
> адресе с паролем по умолчанию — это ровно тот случай, когда пароль по умолчанию и
> стоило бы поменять, а лучше не открывать порт вовсе.

### 10.2. Автоматический деплой

> **TODO(#build-on-server): перенести сборку образа из сервера в CI.**
>
> Сейчас образ собирается на самом сервере (`docker compose up -d --build`) — это
> было осознанным решением для одного сервера, и для первого ручного деплоя оно
> даже удобно. Но у него три цены, и на тестовой машине с 2 ГБ RAM они уже видны:
>
> 1. **Сборка съедает всю память машины.** Gradle и npm на пике берут 2–4 ГБ, то есть
>    на VPS с 2 ГБ это OOM. Образование приходится прерывать, и деплой становится
>    непредсказуемым.
> 2. **~8 ГБ диска уходит под build cache** — столько же, сколько занимает полезный
>    образ.
> 3. **Каждый деплой занимает 2–4 минуты** вместо секунд, потому что кэш между
>    прогонами холодный.
>
> Как чинить: сборка образа переезжает в `ci.yml`, а `deploy.yml` только доставляет
> готовый образ и перезапускает контейнеры. Варианта два — реестр образов
> (GitHub Container Registry) или `docker save` + передача по SSH; выбирать нужно
> по фактической квоте на хранение пакетов, см. раздел [10.2.1](#1021-выбор-между-сборкой-на-сервере-и-реестром-образов).
>
> **Пока это не сделано, деплой на сервере требует swap** — иначе сборку убивает
> OOM-killer. См. [8.5.1](#851-swap-для-сборки-образа-на-сервере).

#### 10.2.1. Выбор между сборкой на сервере и реестром образов

| | Сборка на сервере | Реестр (GHCR) | `docker save` + SSH |
|---|---|---|---|
| Место хранения | build cache на сервере | пакеты GitHub | временный tar на сервере |
| RAM на деплой | 2–4 ГБ на пике | 0 | 0 |
| Место | ~8 ГБ кэша | квота пакета | ~300 МБ временно |
| Нужны токены | нет | `packages: write`, вход на сервере | нет |
| Время деплоя | 2–4 минуты | секунды | минута (передача) |

Квота важнее, чем кажется: на бесплатном аккаунте GitHub пакеты занимают 500 МБ, а
образ этого проекта — 712 МБ. Если квота не действует, `docker save` + SSH —
вариант без лишних сущностей: реестр не нужен, токены для образов не нужны.

Файл `.github/workflows/deploy.yml` уже добавлен в проект. Он подключается к
серверу по SSH, выполняет три вещи:

1. `git reset --hard origin/main` — сервер приводится к состоянию `main`;
2. `docker compose up -d --build app` — контейнер пересобирается и перезапускается;
3. ждёт ответа `/actuator/health` и только после этого считает деплой успешным.

Третий шаг — главный. Без него битый деплой выглядел бы зелёным, и заметить его
можно было бы только по жалобам.

Чтобы заработало, нужны только секреты из [раздела 7.3](#73-секреты-github).
Проверить можно так: вкладка **Actions → Deploy → Run workflow**, либо сделать
коммит в `main` и посмотреть вкладку Actions.

### 10.3. Что происходит при публикации

| Момент | Что происходит | Время |
|---|---|---|
| Коммит в `main` | Запускается `Deploy` | сразу |
| `git reset --hard` на сервере | Код обновлён | секунды |
| `docker compose up -d --build app` | Сборка образа | 2–4 минуты |
| Старт контейнера | Применяются миграции Flyway, поднимается JVM | ~30 секунд |
| Проверка живости | Ждёт `UP` | до 200 секунд |

Во время сборки сайт продолжает работать: старый контейнер остановлен только на
моменте запуска нового. Минута-полторы недоступности — это нормально для этого
проекта, чтобы сделать недоступность нулевой, нужна схема с двумя экземплярами и
балансировщиком, что для сервиса на одного пользователя избыточно.

## 11. Откат

Откат в этом проекте — это откат кода плюс понимание, что с миграциями.

### 11.1. Откат кода

```bash
# на сервере
cd /srv/analizer
git log --oneline -5                       # найти коммит, который был до сбоя

docker compose stop app
git reset --hard <хэш-нужного-коммита>
docker compose up -d --build app
curl -fsS http://127.0.0.1:8080/actuator/health
```

В GitHub этого делать не нужно: пуш в `main` с откатом — тоже нормальный способ,
и он сохранит историю.

### 11.2. Откат миграций

**Откат кода не откатывает миграции.** Flyway применяет их при старте и не умеет
откатывать сам; добавление файла `U3__...sql` работает в коммерческой версии, а в
этом проекте отката нет вообще.

Отсюда правило, важное для всего пайплайна:

> **Миграция должна быть совместима и со старым кодом, и с новым.**
> Иначе откатить сломанный релиз будет нечем.

Это значит:

- добавлять колонку — можно: старый код её не увидит и не сломается;
- удалять колонку или переименовывать — нельзя в том же коммите, где код начинает
  её использовать. Сначала переименование в две колонки, потом код, потом удаление
  старой — три шага, три деплоя;
- переименование таблицы — то же самое.

Проверка «применимы ли миграции» уже есть: это задание `integration` в `ci.yml`,
где Flyway накатывается на пустую базу внутри контейнера.

### 11.3. Потерянные данные

Откат кода не восстанавливает данные. Если испорчены данные — только из резервной
копии, и это уже следующий раздел.

## 12. Резервные копии

Данные лежат в томе `analizer-pgdata`. Удалить том — значит удалить базу.

Простейшая рабочая схема — ночной `pg_dump` в отдельный каталог на этом же сервере
плюс копия этого каталога куда-то ещё (иначе бэкап умрёт вместе с сервером).

```bash
mkdir -p /srv/backups
nano /usr/local/bin/analizer-backup
chmod +x /usr/local/bin/analizer-backup
```

```bash
#!/usr/bin/env bash
set -euo pipefail
STAMP=$(date +%Y%m%d-%H%M%S)
cd /srv/analizer
docker compose exec -T postgres \
  pg_dump -U analizer -d analizer --clean --if-exists \
  | gzip > "/srv/backups/analizer-$STAMP.sql.gz"
# неделю храним
find /srv/backups -name 'analizer-*.sql.gz' -mtime +14 -delete
```

```bash
# раз в сутки в 4:17 — минута не круглая, чтобы не совпасть с другими задачами
(crontab -l 2>/dev/null; echo "17 4 * * * /usr/local/bin/analizer-backup") | crontab -
```

Проверить, что копия читается (пустой файл — самая частая ошибка):

```bash
gunzip -c /srv/backups/analizer-*.sql.gz | head -5
```

Восстановление — это остановка приложения и загрузка дампа обратно:

```bash
cd /srv/analizer
docker compose stop app
gunzip -c /srv/backups/analizer-2026-10-07-041700.sql.gz \
  | docker compose exec -T postgres psql -U analizer -d analizer
docker compose up -d app
```

> У копий на том же сервере две проблемы: они занимают место и умирают вместе с
> сервером. Копии побольше и пореже — наружу, на другое хранилище.
> 🔍 **[Резервные копии, хранение и проверка восстановления](#резервные-копии)** —
> синхронизация с облачным хранилищем, срок хранения, как проверять, что копия
> восстанавливается.

## 13. Обновления приложения

Обычное изменение ничего особенного не требует: коммит в `main` — деплой сам.

Особый случай — **изменение настроек**. Файл `.env` лежит на сервере и из
репозитория не приходит, поэтому:

- добавили переменную в `.env.example` → дописать её в `.env` на сервере и
  перезапустить: `docker compose up -d app`;
- поменяли значение по умолчанию в коде → без `.env` подхватится новое значение.

Ещё один случай: **изменение схемы БД**. Миграция применяется сама, но перед
деплоем стоит убедиться, что она применима к **непустой** базе, а не только к
пустой, как в тестах.

## 14. Если что-то пошло не так

| Симптом | Где смотреть | Что обычно означает |
|---|---|---|
| Сайт не открывается | `curl -I https://домен`, `systemctl status caddy` | Домен ещё не разрешился, или не открыт порт 80/443 |
| Страница есть, вход не работает | логи приложения | Забыли `COOKIE_SECURE=true` вместе с `SameSite=None`: кука не принимается |
| `401` на каждом запросе при успешном входе | то же | То же самое |
| Деплой «прошёл», а сайт старый | вкладка Actions, лог задания | `git reset` не дал эффекта, либо деплой упал на проверке живости |
| Приложение не стартует | `docker compose logs --tail 200 app` | Смена схемы, несовместимость версий, неверный `DB_URL` |
| База не отвечает | `docker compose ps`, `docker compose logs postgres` | Память, место на диске, повреждённый том |
| Медленно грузится | `docker stats` | Не хватает RAM, либо swap съеден сборкой Gradle |
| Ошибка в миграции | `select * from flyway_schema_history` | Несостоявшаяся миграция: чинить руками в БД, предварительно сделав дамп |

Общая последовательность, когда что-то непонятно:

```bash
cd /srv/analizer
docker compose ps                      # кто жив
docker compose logs --tail 100 app     # что сказал приложение
curl -fsS http://127.0.0.1:8080/actuator/health
docker stats --no-stream               # не кончилась ли память
df -h                                  # не кончился ли диск
```

  России и списание в валюту.
- Что такое виртуальный IP, снапшоты диска, вынос IP — стоит ли брать с запасом.
- Смена тарифа без простоя: у большинства провайдеров это просто «изменить план».
- Оплата: карта иностранной картой, СБП, двухфакторная авторизация на панели.

### Домен и DNS {#домен-и-dns}

- Зоны `.ru` и международных доменов: где регистрировать, что дешевле.
- Делегирование: NS-записи, чем делегирование отличается от простого A.
- TTL: как время распространения связано с переездом на другой IP.
- Нужен ли отдельный DNS-провайдер, или достаточно того, где куплен домен.
- Как проверить домен перед покупкой: занятость, история, репутация.

### Docker и окружение {#установка-docker}

- Разница между `docker` и `docker compose`, что такое тома и сети.
- Кэш слоёв: почему вторая сборка быстрее, как его сбросить.
- `docker system prune`: что удаляет и почему это может удалить нужное.
- Ограничения памяти и CPU у контейнеров.

### Rootless и другие движки {#rootless-и-дocker}

- Docker в режиме без прав root, Podman.
- Docker Swarm — почему для одного сервера он не нужен.
- Kubernetes — что это и почему начинать с него для такого проекта не стоит.

### HTTPS {#caddy-или-nginx}

- Как устроены сертификаты Let's Encrypt, что такое ACME-протокол.
- Срок действия сертификата, как происходит автопродление.
- Wildcard-сертификаты для поддоменов.
- Почему нельзя «просто включить HTTPS» без прокси и что такое TLS-терминация.

### Ресурсные ограничения {#устройство-хостинга}

- Почему автоматическая догрузка данных в приложении сэкономит квоту.
