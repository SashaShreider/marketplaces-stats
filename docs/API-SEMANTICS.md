# Смысл API

О том, что означают ответы. Форма — пути, параметры, поля и их типы — описана в
машинном контракте: [`docs/openapi.json`](openapi.json) (OpenAPI 3.1) и `GET /v3/api-docs`
на живом сервере. Интерактивно посмотреть его можно в Swagger UI.

Этот файл объясняет **смысл**: что означает число, когда ноль бывает обманчивым,
почему расходы по товарам меньше дневных, почему отчёт за незагруженный день —
это не ошибка. Форма в нём намеренно не дублируется: контракт меняется вместе с
кодом и проверяется тестом, а пересказ полей в тексте устаревает первым.

## Как устроен API

Три группы методов, различающиеся по побочным эффектам. По префиксу пути сразу видно,
изменит запрос данные или нет.

| Префикс | Что делает | Ходит в API маркетплейса | Тратит квоту |
|---|---|---|---|
| `/imports` | **Команды.** Запускает загрузку данных | **да** | **да** |
| `/data` | Состояние нашей базы: что загружено, что нет | нет | нет |
| `/analytics` | Отчёты, посчитанные по нашей базе | нет | нет |

**Правило, из которого следует всё остальное:** только группа `imports` имеет побочные
эффекты. Методы `data` и `analytics` можно вызывать часто и без риска исчерпать квоту.

**Магазин — сегмент пути `{accountId}`.** Это идентификатор ресурса, а не деталь
реализации: клиент знает, *что* хочет, а как это добыть — дело адаптера. Добавление
Wildberries не меняет ни одного пути.

```
/api/accounts/{accountId}/imports/finance
/api/accounts/{accountId}/data/coverage
/api/accounts/{accountId}/analytics/daily
```

**Маркетплейс — тип, а не магазин.** Он указывается один раз, при подключении:
`POST /api/accounts` с полем `marketplace`. В остальных запросах кода маркетплейса нет,
потому что он выводится из магазина. Если бы он остался в пути, пришлось бы проверять,
что он совпадает с платформой магазина, и два источника правды могли бы разойтись.

Сам маркетплейс в пути раньше означал и тип, и выбор магазина сразу — это работало,
пока магазин на платформе был один. У продавца бывает несколько кабинетов OZON, и
выбор стал бы неоднозначным, а молча взять не тот значило бы показать чужие данные.

## Вход и доступ

**Без сессии доступ закрыт.** Любой метод, кроме перечисленных ниже, отвечает
`401`. Отдельной страницы входа сервер не отдаёт и на неё не редиректит: код ответа
достаточен, а какую страницу показать, решает фронтенд.

| Метод | Открыт | Назначение |
|---|---|---|
| `POST /api/auth/register` | да | завести пользователя |
| `POST /api/auth/login` | да | войти и получить куку |
| `GET /api/auth/csrf` | да | получить CSRF-токен |
| `GET /actuator/health` | да | проверка живости |
| `GET /v3/api-docs` | да | машинный контракт API |
| всё остальное | **нет** | требует сессии |

### Машинный контракт

`GET /v3/api-docs` отдаёт весь API в формате OpenAPI 3.1. Он открыт, потому что по нему
генерируются типы до входа — иначе фронтенд пришлось бы собирать вслепую.

```
npx openapi-typescript docs/openapi.json -o frontend/src/api/schema.d.ts
```

Файл `docs/openapi.json` лежит в репозитории и проверяется тестом на расхождение с кодом:
после изменения любого метода его нужно пересобрать, иначе сборка упадёт. Команда
пересборки приведена в [README](../README.md).

### Порядок первого запроса

```
GET  /api/auth/csrf      → кука XSRF-TOKEN и значение токена
POST /api/auth/register  → 201, логин и отображаемое имя
POST /api/auth/login     → 200, кука JSESSIONID
GET  /api/accounts       → 200, список подключённых магазинов
POST /api/accounts       → 201, подключить магазин
POST /api/accounts/{accountId}/imports/…  → запустить импорт
```

### Если фронтенд запущен отдельно

По умолчанию приложение отвечает только своему источнику, и CORS-заголовков в ответе нет
вообще. Если фронтенд поднят на другом порту, браузер выбросит ответ, и это выглядит как
«сервер молчит» — на деле это запрет на стороне клиента.

Адрес разрешённого источника задаётся переменной `APP_ALLOWED_ORIGINS`:

```
APP_ALLOWED_ORIGINS=http://localhost:5173
```

Два заголовка обязательны и появляются только при заданном списке:
`Access-Control-Allow-Origin` и `Access-Control-Allow-Credentials: true`. Второй нужен,
чтобы браузер приложил куку сессии: без него запрос выглядит анонимным и получает `401`
при заведомо верном пароле.

Предварительный запрос `OPTIONS` проходит **до** проверки CSRF. Если бы порядок был
обратным, `OPTIONS` отклонился бы, браузер не отправил бы сам запрос, а в консоли
лежала бы пустая ошибка сети без кода.

Для публикации по HTTPS задайте `COOKIE_SAME_SITE=None` и `COOKIE_SECURE=true`. С
кукой `SameSite=None` без `Secure` браузер её не примет, а с `Secure` на обычном HTTP —
тоже: сессия будет теряться на каждом запросе.

### Регистрация и вход

**`GET /api/auth/csrf`** формально открыт, но нужен всем остальным: методы, меняющие
состояние, требуют заголовок `X-XSRF-TOKEN`. Токен лежит в куке `XSRF-TOKEN` **и** в
ответе — отправлять нужно и куку, и заголовок с тем же значением, именно так работает
браузер.

**`POST /api/auth/register`** заводит пользователя. Сессия **не** создаётся: первый
экран после регистрации — предсказуемая форма входа. Логин уникален, пароль хранится
BCrypt-хэшем, пустое отображаемое имя подставляется по логину. Восстановления пароля
нет: почта не запрашивается, забытый пароль восстанавливается только правкой базы.

**`POST /api/auth/login`** возвращает куку сессии. Неверные данные дают `401`, а не
`400`, и текст одинаков для «нет такого логина» и «не тот пароль» — иначе перебор
логинов упрощался бы.

**`POST /api/auth/logout`** уничтожает сессию, и старая кука перестаёт работать.

**`GET /api/auth/me`** — отдельная проверка входа: `200` с пользователем либо `401`.
Фронтенд вызывает его при старте и решает, показать приложение или форму входа.

### Магазины

**`POST /api/accounts`** подключает новый магазин. Это отдельный шаг после регистрации,
а не её часть: ключи истекают, менять их приходится, и менять аккаунт для этого не нужно.

Маркетплейс указывается здесь — это тип создаваемого магазина. Два магазина одной
платформы заводятся без помех: у каждого свой `clientId`. Повторное подключение того же
кабинета — `409`: два аккаунта с одинаковыми реквизитами означали бы, что один кабинет
импортируется дважды, дважды съедает квоту и делится на два отчёта.

Секретный ключ не возвращается ни здесь, ни в каком-либо другом ответе, и не пишется
в логи. Проверяется это тестом, а не комментарием. Перед сохранением ключи проверяются
настоящим запросом к маркетплейсу: иначе пользователь узнал бы о неверном ключе через
три неудачных импорта.

> `TODO(#encrypt-credentials)`: ключ хранится в открытом виде. Утечка дампа базы даёт
> доступ ко всем магазинам; планируется AES-GCM и мастер-ключ в `APP_ENCRYPTION_KEY`.
> С несколькими магазинами на пользователя цена такой утечки выше.

**`PUT /api/accounts/{accountId}/credentials`** заменяет реквизиты уже подключённого
магазина. Магазин не создаётся, а чинится тот, что уже есть. Повторная отправка тех же
ключей безопасна и просто перезаписывает их, а вот `POST /api/accounts` с теми же
реквизитами вернёт `409`: подключение создаёт, а эта замена чинит.

**`DELETE /api/accounts/{accountId}`** удаляет подключение магазина **вместе со всеми его
данными**: начислениями, каталогом товаров, днями и прогонами импорта. Остальные
магазины пользователя не затрагиваются. Метод необратим, и это не опечатка в интерфейсе:
восстановить можно только повторным импортом из OZON, то есть заново потратив квоту.
После удаления магазин пропадает из `GET /api/accounts`, и его можно подключить заново.
Справочник маркетплейсов и общий справочник типов начислений не удаляются: они не
принадлежат пользователю.

## Правила общие для всех методов

### Идентификатор магазина

Магазин передаётся в пути: `/api/accounts/{accountId}/...`. Идентификатор берётся из
`GET /api/accounts` при загрузке интерфейса.

Проверка принадлежности выполняется в каждом обращении: запрос идёт по паре
«идентификатор + текущий пользователь», а не по одному идентификатору. Чужой
магазин и несуществующий дают одинаковый `404` — различая их, мы сообщали бы, какие
магазины существуют.

Магазинов у пользователя сколько угодно, в том числе несколько на одной платформе:
у продавца бывает несколько кабинетов OZON, и у каждого свои начисления и каталог.
Ограничение в базе — `UNIQUE (app_user_id, marketplace_id, client_id)`: разные
кабинеты разрешены, один и тот же дважды — нет.

> Раньше был параметр `?clientId=`. Это идентификатор OZON — у Wildberries он называется
> `companyId`, и выставлять его в общем API значило зашить в контракт одно конкретное
> имя. Сейчас в пути внутренний идентификатор магазина, а `clientId` возвращается
> только в ответе списка — чтобы человек мог различить два кабинета с одинаковым
> названием.
>
> Попытка открыть чужой прогон импорта по номеру даёт `404`, а не чужие данные: иначе
> перебором номеров можно было бы увидеть чужой магазин.

### Даты

ISO 8601, формат `ГГГГ-ММ-ДД`. Обе даты включительные: `dateFrom=2026-09-01&dateTo=2026-09-30`
означает 30 дней. `dateTo` раньше `dateFrom` — ошибка `400`.

### Знаки сумм

Суммы хранятся **со знаком, как их отдаёт OZON**: доход положителен, расход отрицателен.
Это делает отчёт сравнимым с личным кабинетом. Там, где клиенту нужен положительный
расход, есть отдельные поля.

Тождество отчёта, проверенное на реальных выгрузках:

```
доходы − расходы = к выплате
```

### Ключи с `null`

Поля со значением `null` **присутствуют в ответе**, а не отсутствуют. Клиент может
рассчитывать, что ключ есть.

### Полные ответы — всегда

Все методы возвращают полный объект, а не только запрошенную часть. Это дороже по
трафику, но позволяет расширять контракт, не ломая клиентов.

## Импорты

Единственная группа с побочными эффектами. Загрузка всегда **фоновая**: POST сразу
возвращает номер прогона, работа продолжается после ответа.

Месяц — десятки обращений к OZON, год — сотни. Если ждать их внутри HTTP-запроса,
клиент отвалится по таймауту, хотя данные наполовину загрузятся.

**`POST /api/accounts/{accountId}/imports/finance`** запускает импорт начислений за
период. Догружаются только недостающие дни: уже загруженные окончательные дни повторно
не запрашиваются, поэтому повторный запуск не создаёт дублей и не тратит квоту зря.
Аккаунт создаётся автоматически, если его ещё нет: на чистой установке первый же
импорт и должен приводить систему в рабочее состояние. Может вернуть `409`, если уже
идёт импорт пересекающегося периода — два процесса писали бы одни и те же операции.

**`POST /api/accounts/{accountId}/imports/catalog`** запускает импорт характеристик
товаров: названий, ISBN, авторов, обложек. Периода у каталога нет, поэтому дат в
запросе не бывает. Каталог каждый раз переписывается целиком: OZON не сообщает, какие
товары изменились, а выборочный перебор стоил бы столько же запросов.

Обход идёт с `visibility=ALL`, а это по документации OZON «все товары, **кроме
архивных**». Поэтому после обхода отдельно добираются SKU, которые есть в начислениях,
но не пришли: такими могут быть только снятые с продажи. Добор точечный, одним запросом
на недостающие SKU, а не обходом архива — архив растёт со временем и обходился бы заново
при каждом запуске. Найденные товары сохраняются как обычные, но с `archived: true`.

Импорт каталога **не** блокирует финансовый: у того другая логика конфликта.

### Ответ импорта — `ImportProgress`

Один и тот же объект возвращается при запуске и при опросе прогресса.

| Ключ | Что означает |
|---|---|
| `id` | Номер прогона. Используйте в `GET /imports/{importId}` |
| `importType` | `FINANCE` — начисления, `CATALOG` — товары |
| `dateFrom` / `dateTo` | Период финансового импорта. `null` у каталога |
| `status` | Состояние прогона, см. ниже |
| `totalUnits` | **Единиц работы всего.** Дней у финансового импорта, товаров у каталога |
| `doneUnits` | Успешно обработано |
| `skippedUnits` | Пропущено как уже загруженное |
| `failedUnits` | Не удалось обработать. Такие единицы числятся **неудавшимися, а не пустыми** |
| `currentUnit` | Дата в работе у финансового импорта, SKU — у каталога |
| `error` | Причина неудачи. Заполняется при `status: FAILED` |
| `createdAt` / `startedAt` / `finishedAt` | Когда прогон создан, начался и закончился |
| `inProgress` | **`true`, пока импорт идёт.** Опрашивайте, пока не станет `false` |
| `percent` | Готовность 0–100, считается с учётом пропущенных и упавших |

**Значения `status`:**

| Значение | Что означает | Что делать в UI |
|---|---|---|
| `PENDING` | Создан, работа ещё не началась | Показать ожидание |
| `RUNNING` | Идёт | Полоса прогресса по `percent` |
| `DONE` | Завершён без ошибок | Показать результат |
| `FAILED` | Часть единиц не удалась или прогон упал целиком | Показать `error`, предложить повторить |
| `CANCELLED` | Отменён | Показать как прерванный |

**Прогресс виден по ходу, а не в конце.** `doneUnits` растёт по мере сохранения,
поэтому результат доступен до окончания импорта.

**`GET /api/accounts/{accountId}/imports`** отдаёт последние прогоны, новые сверху, не
более двадцати. Это **всегда массив**, даже если прогонов ещё не было: клиенту не нужно
различать пустой список и `null`. Фильтра по виду импорта нет: клиенту полезно видеть и
финансовые, и импорты каталога в одной истории.

**`GET /api/accounts/{accountId}/imports/{importId}`** отдаёт прогресс одного прогона.
`404` — прогона с таким номером нет **или он принадлежит другому аккаунту**.

## Состояние данных

### `GET /api/accounts/{accountId}/data/coverage`

Что загружено, чего не хватает и какие данные ещё не окончательные.

> **Про один день.** Чтобы узнать состояние одного дня, передайте одинаковые `dateFrom`
> и `dateTo`. Отдельного метода «про день» нет намеренно: он был бы тем же запросом с
> другим числом параметров.

Отвечает и до первой синхронизации — отсутствие данных это ответ, а не ошибка.

**Зачем `provisionalDays`.** Начисления за текущий день продолжают приходить в течение
суток, а за вчерашний могут появиться позже — возвраты и корректировки. Такие дни
загружены, но доверять им как окончательным нельзя.

**Зачем `finalDays`.** Окончательным день считается не по дате, а по изменению суммы:
при каждой повторной загрузке сумма сравнивается с предыдущей. Пока сумма меняется,
день не окончательный.

**`needsSync`** — единственный признак, который говорит «есть смысл предлагать
загрузку». Остальные поля показывают, что именно отсутствует.

### `GET /api/accounts/{accountId}/data/catalog`

Состояние каталога товаров: **количество и дату последней загрузки**, а не сами товары —
чтобы посмотреть товары вместе с финансами, есть `/analytics/products`.

> `loaded: false` при `products: 0` означает «каталог ещё ни разу не импортировался»,
> а **не** «у продавца нет товаров».

### `GET /api/accounts/{accountId}/data/authors`

Варианты авторов для подсказок фильтра.

Список строится из того, что **реально ввёл продавец**, поэтому может содержать
странные значения: если вместо имени написаны инициалы, подсказка повторит инициалы.
Это честнее, чем предлагать несуществующие написания.

В списке лежат ровно те строки, которые найдут товары, поэтому значение из подсказки
можно **передать в параметр `author` как есть**. Рядом могут стоять «Сурцуков А.»,
«Сурцуков Анатолий» и «А.В. Сурцуков» — это три написания одного человека, и свести
их к одному может только продавец, в карточках товара.

## Аналитика

### `GET /api/accounts/{accountId}/analytics/daily`

Разбивка доходов, расходов и выплаты по дням, с детализацией расходов по типам
начислений.

В `days` попадает по одному объекту на **каждый** день периода, включая дни без
начислений.

**Значения `status`:**

| Значение | Что означает | Что делать в UI |
|---|---|---|
| `READY` | Все дни загружены, ошибок нет | Показывать цифры как есть |
| `PARTIAL` | Часть дней загружена, часть — нет | Плашка «показаны неполные данные» + кнопка догрузки |
| `NOT_LOADED` | Ни один день не загружен | Плашка «данных нет» + кнопка загрузки |
| `HAS_ERRORS` | Хотя бы один день не удалось загрузить | Плашка с ошибкой + кнопка повтора |

**Знаки в ответе.** Раскладка внутри дня и внутри периода — со знаками, как в OZON:
продажи положительны, возвраты отрицательны, бонусы и ковейст — доход, комиссия и
логистика — расход. Но `income` и `expenses` верхнего уровня положительны: это итоги,
а не слагаемые. `reconciled` означает `income − expenses = payout` по каждому дню;
`null` — если выплата неизвестна (см. «Выплата при отборе неизвестна»).

**Где искать количество за период.** Только в `total.soldQuantity` и
`total.returnedQuantity` — на верхнем уровне их нет, в отличие от денег. Это известная
непоследовательность формы ответа, помечена `TODO(#response-duplication)` в коде.
Суммировать `days[].soldQuantity` не нужно: результат тот же, а лишний проход по
массиву.

**Количество в строке дня.** Два отдельных числа, а не одно: `soldQuantity` и
`returnedQuantity`. Возвраты в `soldQuantity` **не входят**, и уменьшать одно на другое
не нужно — сложение покажет чистую цифру, а молча уменьшенное число читалось бы как
«продали N», хотя на самом деле продали N плюс ещё несколько и часть вернули.

Что **не** попадает в количество: строки начислений, у которых OZON не прислал
`sale_price`. Это удержания и штрафы за доставку, они приходят с `quantity`, равным
единице, но продажами не являются. Включение дало бы завышение примерно на двадцать
процентов — на реальных данных сентября 2026 это 119 единиц против 555 настоящих продаж.

**Отбор: `author` или `skus`.** Отчёт можно ограничить автором (`?author=Сурцуков А.`)
или списком товаров (`?skus=1&skus=2`). Это не подмена запроса, а сужение отчёта:
доходы, расходы, прибыль и раскладка расходов считаются только по выбранному, и одно
и то же число в разных отборах означает разное — поэтому подпись отбора едет вместе с
цифрами в поле `filter` («Все товары», имя автора или «SKU 1, 2, 3 и ещё 4»).

**Товары сильнее автора.** Если переданы оба параметра, применяется отбор по `skus`,
а `author` игнорируется: выбрав товар, пользователь уже ответил, чей он. Пустая строка
в `author` и пустой список `skus` означают «без отбора», а не «ничего не найдено».

**Что происходит с расходами без товара.** Начисления `NON_ITEM` и `CONTAINER` не
привязаны ни к какому SKU, и распределить их между товарами можно только выдумав
правило. Поэтому при любом отборе они в цифры **не входят**, а их сумма приходит
отдельно — в `unallocatedExpenses`. Показывать её обязательно: иначе усечённая прибыль
выглядит полной. При отчёте по всему магазину поле равно нулю, потому что такие расходы
в него уже вошли.

**Выплата при отборе неизвестна.** `total_amount` OZON отдаёт по всему магазину, и
вычленить из него долю нескольких товаров нечем. Поэтому при `scoped = true` поля
`payout` (верхнего уровня, в `total` и в строке дня) приходят **`null`**, а
`reconciled` — тоже `null`. Ноль в выплате означал бы «выплаты не было», а `false` в
`reconciled` — «не сходится»; и то и другое было бы вымыслом. Прибыль в отчёте по части
товаров считается как `income − expenses`: сверять её с выплатой нельзя.

**Детализация расходов по типам.** У каждой статьи есть служебное название из
справочника (`PayPerClick`, `StarsMembership`), человеческое описание из того же
справочника («Оплата за клик») и сумма с отрицательным знаком.

Показывать пользователю следует описание: `PayPerClick` продавец не поймёт, а «Оплата за
клик» поймёт. Служебное название оставлено для случаев, когда описание пустое.

Справочник типов открыт и пополняется, поэтому опирайтесь на названия, а не на
идентификатор типа: он устойчив к переименованию, но нечитаем. Тип, которого в
справочнике нет, придёт с именем «Тип 12345» и пустым описанием — это честнее, чем
потерять расход молча.

**`expenseBreakdown` — расходы по крупным статьям.** `expensesByType` покрывает только
начисления по товару и без SKU: в нём нет ни комиссии, ни логистики, и рядом с полной
суммой расходов он читается как её часть. `expenseBreakdown` покрывает расходы целиком:

```
комиссия + логистика + прочие = все расходы периода
```

Статьи: `COMMISSION`, `PROMOTION`, `LOGISTICS`, `STORAGE`, `ACQUIRING`, `OTHER`.
Статья, которой магазин не пользуется, в `groups` не приходит вовсе — ноль в ней
читался бы как поломка.

Раскладка приходит в двух местах: `expenseBreakdown` верхнего уровня — за период (его
читает карточка расходов), и `days[].expenseBreakdown` — за день (строки таблицы).
Сумма в `total` — со знаком, как у OZON: возврат комиссии её уменьшает. `expenses`
верхнего уровня по-прежнему положителен, поэтому сверять надо `|total|`, а не `total`.

Статья определяется по названию типа начисления, а не по его номеру: справочник
обновляется, и номеров может стать больше. Исключение — логистика: её статья берётся
из того, откуда пришло начисление (услуга доставки в строке товара), потому что типов
доставки десяток и их список меняется. Неизвестный тип попадает в `OTHER`, а не
пропадает.

### `GET /api/accounts/{accountId}/analytics/products`

Все товары каталога вместе с их продажами и списаниями за период.

**Сортировка выполняется в базе до разбиения на страницы:** на первой странице с
`sort=INCOME` находятся лучшие продажи всего каталога, а не той выборки, что попала в
страницу. Товары с одинаковым доходом упорядочены по SKU — иначе они прыгали бы между
страницами при перелистывании. Неизвестное значение сортировки трактуется как `INCOME`.

Критерий сортировки — по одному на колонку таблицы:

| `sort` | Что упорядочивает | Направление по умолчанию |
|---|---|---|
| `INCOME` | доход товара | по убыванию |
| `SOLD` | единиц продано | по убыванию |
| `EXPENSES` | расходы товара | по убыванию |
| `GROSS` | выручка, то есть доход минус расходы | по убыванию |
| `NAME` | название товара | по возрастанию |
| `SKU` | артикул | по возрастанию |

Направление задаётся отдельно: `order=asc` или `order=desc`. Если оно не задано,
берётся то, что привычнее для критерия, — по именам по возрастанию, по деньгам и
количествам по убыванию.

**Отбор `onlyWithSales=true` оставляет только товары, у которых были продажи.** Счётчик
`productsWithSales` в итогах отчёта считает то же самое, поэтому число строк отбора и
этот счётчик совпадают. Товары без продаж при этом не исчезают из каталога — они просто
не попадают в такой отбор.

**Итоги — по всем товарам периода, а не по текущей странице.** Иначе листание
страниц меняло бы итоги.

**Числа в строке товара.** `soldQuantity` и `returnedQuantity` — единицы за период,
возвраты не вычтены. `accrualCount` — сколько операций затронуло товар. `archived`
означает, что товар снят с продажи и убран в архив OZON: в кабинете его уже нет, но
начисления остались.

**`financial.reconciles` у товара может быть `false`, и это нормально.** Выплата
приходит на начисление целиком, а начисление может относиться сразу к нескольким
товарам, поэтому распределить её между ними — значит выдумать пропорцию. Тождество
проверяется на уровне периода (`reconciled` в дневном отчёте), а не на уровне товара.

**`soldQuantity` и `productsWithSales` — не одно и то же.** Первое это единицы,
второе — сколько товаров хоть что-то продали. Ошибиться здесь легко и заметно только
при сверке с кабинетом.

**Расходы по товарам меньше дневных** — расходы типов `NON_ITEM` и `CONTAINER` приходят
от OZON без привязки к SKU. Такая сумма показана отдельным полем `unallocatedExpenses`,
и именно поэтому сверка отчёта по товарам с дневным отчётом выглядит так:

```
income − expenses − payout = unallocatedExpenses
```

**`skusMissingFromCatalog`** — SKU из начислений, которых нет в каталоге. Их нельзя
показать в отчёте по товарам, и молчать о них нельзя: иначе расхождение сумм
необъяснимо.

**Отбор по автору строгий** — см. [четыре вещи, которые часто понимают
неправильно](#3-фильтр-по-автору-строгий).

### `GET /api/accounts/{accountId}/analytics/products/dynamics`

Продажи и возвраты по дням периода — **в штуках**, не в деньгах. Отдельный метод от
`/analytics/products`, а не поле в нём: там строки это товары, и без этого запроса
пришлось бы скачивать весь отчёт только ради рисунка.

`author` и `sku` — **два взаимно исключающих отбора**. При заданном `sku` автор
игнорируется: иначе пришлось бы искать товар сразу у двух продавцов, а задача у
пользователя одна.

**Дни без операций в `days` не попадают** — пропуски восстанавливает клиент по датам.
Состояние незагруженных дней приходит в `coverage`, и без него «день без продаж» и
«день не загружен» на графике выглядели бы одинаково.

Товар, которого нет в каталоге (снят с продажи или карточка не загружена), **в динамику
попадает**: его продажи от этого не перестают быть продажами, и сумма под графиком
обязана сходиться с итогами.

Поле `filter` отвечает на вопрос, чем ограничен отчёт: «Все товары», имя автора или
`SKU …`. Оно нужно для подписи над графиком: без него отбор одного товара из сотни
читался бы как данные по всему магазину.

## Четыре вещи, которые часто понимают неправильно

### 1. Ноль бывает разным

**В дневном отчёте** ноль за незагруженный день — это ложь, поэтому день помечается
как незагруженный.

**В отчёте по товарам** ноль у товара, который есть в каталоге, — правда: товар
существует, продаж за период не было. Молчать о нём означало бы скрыть товары, которые
перестали продаваться.

Но если период загружен не полностью, это указано в `status` и `coverage`, и нулям
верить нельзя.

### 2. Расходы по товарам меньше дневных

Расходы типов `NON_ITEM` и `CONTAINER` приходят от OZON **без привязки к SKU**.
Распределить их между товарами можно было бы только выдумав правило, поэтому этого не
происходит, а сумма показана отдельным полем:

```
unallocatedExpenses = 3353.58
totals.expenses     = 13308.45
                       ─────────
                       16662.03  ← столько расходов в дневном отчёте
```

Отсюда **правильная сверка**, а не `income − expenses = payout`:

```
income − expenses − payout = unallocatedExpenses
25280.00 − 13308.45 − 8617.97 = 3353.58 ✓
```

### 3. Фильтр по автору строгий

Ищется ровно то, что введено, — так, как автор назван в карточке товара. Имена у OZON
приходят в разных форматах, и «Сурцуков А.», «Сурцуков Анатолий», «А.В. Сурцуков» и
«Анатолий Васильевич Сурцуков» — это четыре написания одного человека, но фильтр
различает их:

| Запрос | Результат |
|---|---|
| `author=Сурцуков Анатолий` | только товары с таким именем в карточке |
| `author=Сурцуков А.` | только товары с такой формой — другой набор |
| `author=Сурцуков` | ничего: такой строки нет ни в одной карточке |

Регистр значения тоже значения не имеет: `асилий Калязин` найдёт товар, а
`Асилий Калязин` — нет. В выгрузке действительно есть товар с именем, набранным с
маленькой буквы.

**Исключение одно: перечисленные авторы.** Если в карточке их несколько, то подходит
любой из перечисленных. «Черняев А. Ю., Ланде А. А.» разбирается на два значения, и
`author=Ланде А. А.` находит тот же товар, что и `author=Черняев А. Ю.` — искать надо
одно из имён, а не всю строку целиком.

Почему так строго: сведение имён к «фамилия + инициалы» угадывает. Оно склеило бы
разные написания одного человека, но не различило бы «Герланец Валерий» и
«Герланец Валерий Петрович», а людей с общей фамилией склеило бы в одного. В отчёте о
продажах лишний товар — это лишние деньги, поэтому точность важнее удобства.
Унифицировать написание может продавец — в карточках своего кабинета.

### 4. Количество продаж — не всё, у чего есть `quantity`

В начислениях OZON есть строки, у которых количество равно единице, продажей они не
являются, и в счёт не попадают. Это удержания и штрафы за доставку: у них `commission`
равен `null`, поэтому цена продажи неизвестна, а сама операция целиком отрицательная и
равна логистике.

На настоящих данных за апрель и сентябрь 2026 таких строк 139 при 555 настоящих
продажах. Наивное суммирование `quantity` завысило бы количество на 21 процент, и
заметить это можно было бы только ручной сверкой с кабинетом.

Ещё одна ловушка рядом: при `quantity > 1` поле `sale_price` приходит **за всю
позицию**, а не за штуку, и `seller_price` — уже **за единицу**. Делить выручку на
количество нельзя.

## Ошибки

Формат **RFC 7807** (`application/problem+json`) у всех ошибок.

```json
{
  "type": "urn:analizer:error:account-not-found",
  "title": "Магазин не найден",
  "status": 404,
  "detail": "Магазин 999 не найден",
  "instance": "/api/accounts/999/imports"
}
```

| Код | Когда | Дополнительные поля |
|---|---|---|
| `400` | Неверные параметры: нет обязательного, `dateTo` раньше `dateFrom` | — |
| `400` | Маркетплейс отверг реквизиты | `remoteStatus` |
| `401` | Нет сессии, либо неверный логин или пароль | — |
| `403` | Запрос без действующего CSRF-токена | — |
| `404` | Неизвестный маркетплейс — `type: unknown-marketplace` | `marketplace` |
| `404` | Магазина нет или он чужой — `type: account-not-found` | — |
| `404` | Несуществующий прогон импорта | — |
| `409` | Импорт уже идёт | `conflict`, `activeImportId`, `activeImport`, `requestedFrom`, `requestedTo` |
| `409` | Этот кабинет уже подключён — `type: shop-already-connected` | — |
| `409` | Логин уже занят | — |
| `502` | API маркетплейса вернул ошибку | `ozonStatus`, `ozonCode` |

> `401` и `403` в теле ответа не различают «сессии нет» и «токен не тот»: пока пользователь
> анонимен, отказ в доступе отвечает кодом входа, а не запретом. Клиенту достаточно
> знать, что нужно войти заново.
>
> `404` на магазин не различает «нет такого» и «не твой». Иначе перебор идентификаторов
> показывал бы, какие магазины существуют.

### Значения `conflict`

| Значение | Что произошло | Что делать |
|---|---|---|
| `OVERLAPPING_PERIOD` | Идёт импорт пересекающегося периода | Дождаться `activeImportId` |
| `CATALOG_BUSY` | Идёт импорт каталога | Дождаться `activeImportId` |

Значения `SHOP_ALREADY_CONNECTED` и `LOGIN_TAKEN` живут в поле `type` ответа, а не в
`conflict`: последнее поле есть только у конфликтов импорта, где клиенту нужно знать, что
именно дождаться.

**Не является ошибкой.** Отчёт за период, который не загружался, возвращает `200` со
статусом `NOT_LOADED`. Отсутствие данных — это состояние, а не сбой: вернув ошибку,
пришлось бы заставлять клиента угадывать, что произошло.

## Сценарии

### Первый запуск

```http
GET  /api/auth/csrf
POST /api/auth/register                       → 201
POST /api/auth/login                          → 200 и кука сессии
GET  /api/marketplaces                        → какие платформы поддерживаются
POST /api/accounts                            → 201, магазин подключён, id известен
POST /api/accounts/1/imports/catalog
GET  /api/accounts/1/imports/{id}          до inProgress = false
POST /api/accounts/1/imports/finance?dateFrom=…&dateTo=…
GET  /api/accounts/1/imports/{id}          до inProgress = false
GET  /api/accounts/1/analytics/products?dateFrom=…&dateTo=…
```

### Второй магазин того же продавца

```http
GET  /api/accounts                → у пользователя уже есть магазин с clientId 1154
POST /api/accounts  {marketplace: "OZON", clientId: "7777", …}
     → 201, второй магазин; у первого данные остались нетронутыми
POST /api/accounts  {marketplace: "OZON", clientId: "1154", …}
     → 409 shop-already-connected: тот же кабинет подключать второй раз нельзя
```

Смена ключей первого магазина идёт отдельным адресом, чтобы не было неоднозначности,
какой из кабинетов чинить:

```http
PUT /api/accounts/1/credentials  {clientId: "1154", apiKey: "новый"}
```

### Догрузить период

```http
GET  /api/accounts/1/data/coverage?dateFrom=…&dateTo=…
     → смотрим needsSync и missingDays
POST /api/accounts/1/imports/finance?dateFrom=…&dateTo=…
GET  /api/accounts/1/imports/{id}          до inProgress = false
```

Загружаются только недостающие дни. Уже загруженные окончательные не трогаются.

### Отчёт с фильтром по автору

Значение `author` берётся из подсказок — тогда оно гарантированно что-то найдёт.
Регистр и написание сохраняются как есть.

```http
GET  /api/accounts/1/data/authors           подсказки
GET  /api/accounts/1/analytics/products?dateFrom=…&dateTo=…&author=Сурцуков%20А.
```

### Сверка с кабинетом OZON

```http
GET  /api/accounts/1/analytics/daily?dateFrom=…&dateTo=…
     → reconciled = true  значит income − expenses = payout
     → total.sales, total.commission и прочие можно сверить построчно
```

### Бюджет запросов к OZON

| Действие | Запросов |
|---|---|
| Импорт каталога | **1** (108 товаров одним ответом) |
| Один день начислений | 1–2 |
| `refreshAccrualTypes=true` | +1 |
| Месяц начислений | 30+ |
| Любой метод `/data` и `/analytics` | **0** |

Первый прогон делайте как «каталог + один день» — этого хватает, чтобы увидеть всё.

## Ограничения

**Один кабинет подключается один раз.** Ключ в базе — пара «пользователь + маркетплейс +
`clientId`», поэтому несколько кабинетов одной платформы завести можно, а один и тот же
дважды — нет. Двум разным пользователям с одинаковым `clientId` это тоже не мешает:
`clientId` — понятие OZON, а не наше, и он не обязан быть уникальным глобально.

Один кабинет, подключённый дважды, означал бы два импорта одного кабинета, двойной расход
квоты и два отчёта, каждый из которых показывает половину одних и тех же денег.

**Защита от параллельных импортов работает в пределах одного процесса.** При нескольких
экземплярах приложения блокировку нужно перенести в базу. Разные магазины не мешают друг
другу даже сейчас: проверка пересечения ведётся по магазину.

**Период импорта ограничен `2022-01-01`.** OZON не отдаёт более ранние начисления.
