# SPEC — Backend аналитики продаж на маркетплейсах

## 1. Цель проекта

Разработать backend веб-приложения для финансовой аналитики магазина, продающего товары через маркетплейсы.

На первом этапе реализуется интеграция только с **OZON**. Архитектура должна позволять в дальнейшем добавить другие маркетплейсы без изменения основной логики аналитики.

Источник данных — **официальный OZON Seller API**.

Документация OZON API будет предоставлена отдельно.

---

## 2. Что должно делать приложение

Приложение должно:

1. Получать финансовые данные магазина из OZON API.
2. Сохранять полученные данные в собственной базе данных.
3. Сохранять достаточно исходной информации, чтобы в дальнейшем можно было изменять правила расчёта аналитики без повторного получения исторических данных из OZON.
4. Формировать финансовые отчёты за произвольный период.
5. Предоставлять данные через REST API.

На данном этапе **frontend не требуется**. Работу backend необходимо проверять напрямую через REST API.

---

## 3. Основные показатели

В MVP необходимо работать со следующими показателями:

### Продажи

Для продаж необходимо хранить данные, позволяющие определить:

* количество проданных товаров;
* сумму продаж;
* SKU товара;
* дату продажи;
* скидки/бонусы и другие доступные финансовые данные продажи.

Продажей считается соответствующая положительная операция в финансовых данных OZON.

### Возвраты

Необходимо отдельно учитывать возвраты:

* количество возвращённых товаров;
* сумму возвратов;
* SKU;
* дату.

Возвраты должны быть доступны отдельно от продаж.

### Расходы

Необходимо хранить детализацию расходов, поступающих от OZON.

В частности, должны быть доступны:

* комиссия маркетплейса;
* логистика;
* прочие расходы;
* тип/категория расхода;
* сумма;
* дата;
* SKU, если OZON связывает расход с конкретным товаром.

Расходы, которые OZON не связывает с конкретным SKU, не нужно искусственно распределять между товарами.

### К выплате

Необходимо получать показатель **«К выплате»** на основании финансовых операций OZON.

Важно: «К выплате» не является прибылью магазина, поскольку в MVP не учитывается себестоимость товаров.

---

## 4. Отчёты

Данные необходимо хранить таким образом, чтобы можно было построить два основных отчёта.

### Отчёт 1 — ежедневная аналитика

Пользователь выбирает произвольный период.

Для каждого дня необходимо показать:

| Дата | Продажи | Возвраты | Расходы | К выплате |
| ---- | ------: | -------: | ------: | --------: |

Также должны быть доступны итоговые значения за выбранный период.

Расходы должны иметь возможность детализации по категориям.

---

### Отчёт 2 — аналитика по товарам

Пользователь выбирает произвольный период.

Для каждого SKU необходимо показать финансовые показатели за этот период, в том числе:

* количество продаж;
* сумма продаж;
* количество возвратов;
* сумма возвратов;
* расходы, которые можно связать с товаром;
* итоговую сумму к выплате по товару, если она может быть однозначно определена из данных OZON.

Расходы без SKU должны учитываться отдельно и не должны произвольно распределяться между товарами.

---

## 5. Работа с данными OZON

Необходимо изучить предоставленную документацию OZON API и определить, какие данные используются для построения описанных отчётов.

Особое внимание необходимо уделить финансовым операциям различных типов.

Например, финансовые данные OZON могут содержать:

* продажи;
* возвраты;
* комиссию;
* логистику;
* другие начисления и списания.

Необходимо сохранить исходные данные OZON в таком виде, чтобы:

* не потерять информацию, которую предоставляет API;
* иметь возможность повторно интерпретировать данные в будущем;
* не зависеть от текущих правил формирования отчётов.

`accrual_id` должен использоваться для идентификации конкретной финансовой операции.

Необходимо учитывать, что одна операция может содержать несколько товаров, а несколько финансовых операций могут относиться к одной продаже/отправлению.

---

## 6. Синхронизация

Backend должен уметь получать данные OZON за указанный период.

Повторная синхронизация одного и того же периода не должна создавать дубликаты данных.

Полученные данные должны сохраняться в базе независимо от формирования отчётов.

Отчёты должны строиться на основании сохранённых данных, а не напрямую на основании ответа OZON API.

---

## 7. Этапы разработки

Разработка выполняется поэтапно.

### Этап 1 — получение и сохранение данных

Необходимо:

* подключить OZON API;
* получить реальные финансовые данные;
* определить необходимые типы операций;
* сохранить их в БД;
* убедиться, что данные корректно извлекаются и не теряются.

**Контрольная точка:** реальные данные из OZON успешно получены и сохранены в БД.

---

### Этап 2 — финансовая модель

На основании сохранённых данных реализовать определение:

* продаж;
* возвратов;
* расходов;
* суммы к выплате.

**Контрольная точка:** показатели можно проверить вручную на конкретных данных OZON.

---

### Этап 3 — ежедневный отчёт

Реализовать REST API для получения ежедневной аналитики за произвольный период.

**Контрольная точка:** API возвращает корректные значения по каждому дню и итоговые значения за период.

---

### Этап 4 — отчёт по товарам

Реализовать REST API для получения аналитики по SKU за произвольный период.

**Контрольная точка:** данные по товарам корректно агрегируются, а расходы без SKU не распределяются искусственно.

---

### Этап 5 — проверка

Добавить тесты для основных сценариев:

* продажа;
* возврат;
* комиссия;
* логистика;
* прочие расходы;
* несколько финансовых операций для одной продажи;
* несколько товаров в одной операции;
* повторная синхронизация.

---

## 8. Ограничения MVP

В MVP **не требуется**:

* frontend;
* расчёт себестоимости;
* расчёт чистой прибыли;
* учёт заказов как отдельной бизнес-сущности;
* прогнозирование;
* рекламная аналитика;
* интеграция с другими маркетплейсами;
* предварительно рассчитанные дневные/месячные таблицы аналитики.

Главная задача MVP:

> **Получить финансовые данные из OZON API, сохранить их без потери исходной информации и на их основе предоставить два отчёта: ежедневную финансовую аналитику и аналитику по товарам за произвольный период.**
