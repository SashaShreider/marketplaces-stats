# OZON Analizer

Анализ начислений и каталога товаров OZON: дневные и товарные отчёты, сверка с
кабинетом продавца, импорт данных по расписанию.

---

## Что это

Сервис, который сам забирает у OZON финансовые начисления и каталог товаров,
раскладывает их по дням и по товарам и отвечает на вопрос «сколько я заработал и
на чём».

Ключевое свойство отчётов — **они сходятся**. Сумма доходов по дням равна сумме по
товарам, а та равна сумме в кабинете OZON. Это не приблизительное совпадение:
тождества проверяются тестами на каждом прогоне.

Сервис самодостаточный: интерфейс и API отдаёт один процесс с одного порта, своя
база рядом, внешних сервисов кроме OZON не требуется.

## Быстрый старт

Нужен Docker. Java и Gradle ставить не нужно.

```bash
cp .env.example .env      # значения по умолчанию подходят для локальной БД
docker compose up --build
```

Откроется единая точка входа со всем сразу:

| Что | Где |
|---|---|
| Приложение и интерфейс | http://localhost:8080 |
| Проверка живости | http://localhost:8080/actuator/health |
| Контракт API | http://localhost:8080/v3/api-docs |
| Просмотр базы | http://localhost:5050 (`analizer@example.com` / `analizer`) |

Интерфейс лежит в том же образе, что и backend: стадия сборки фронтенда кладёт
собранный `index.html` внутрь `jar`, и Spring Boot отдаёт его сам. Отдельный
веб-сервер не нужен — а вместе с ним отпадают CORS и проблемы с куками сессии.

Дальше всё делается из браузера: зарегистрируйтесь, войдите, подключите маркетплейс
реквизитами OZON. При первом подключении интерфейс сам загрузит текущий период,
потом достроит историю за 90 дней перед ним и дальше будет сам догружать
недогруженные дни.

### Без Docker

Нужны JDK 21, Postgres и Node.js 22.

```bash
cp .env.example .env
docker compose up -d postgres        # только база

# Терминал 1 — интерфейс с горячей перезагрузкой
cd frontend && npm install && npm run dev

# Терминал 2 — backend
.\gradlew.bat bootRun                # или ./gradlew bootRun на Linux/macOS
```

Для этой схемы backend должен разрешить источник фронтенда:

```bash
APP_ALLOWED_ORIGINS=http://localhost:5173
```

Без этого браузер не примет сессионную куку, и каждый запрос будет давать `401`
при успешном входе.

## Доступ

Сессия в куке, а не токен. Сессию можно оборвать — «выйти на всех устройствах» в
схеме с токеном превращается в самописный чёрный список, который потом забывают
чистить.

```
GET  /api/auth/csrf      → кука XSRF-TOKEN
POST /api/auth/register  → 201
POST /api/auth/login     → 200, кука JSESSIONID
```

Дальше каждый запрос сам приносит куку. Для методов, меняющих состояние, значение
XSRF-TOKEN обязательно повторяется в заголовке `X-XSRF-TOKEN`.

**Реквизиты OZON не хранятся в `.env`.** Их вводит пользователь через
`PUT /api/marketplaces/{mp}/credentials`, и перед сохранением они проверяются
настоящим запросом к OZON: иначе о неверном ключе пользователь узнал бы через три
неудачных импорта.

## Настройки

Все настройки задаются переменными окружения; в `.env.example` — с комментариями.

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `DB_URL` | `jdbc:postgresql://localhost:5433/analizer` | База |
| `DB_USERNAME`, `DB_PASSWORD` | `analizer` | Доступ к базе |
| `SERVER_PORT` | `8080` | Порт приложения |
| `APP_ALLOWED_ORIGINS` | пусто | Источники, которым разрешён CORS |
| `COOKIE_SAME_SITE` | `Lax` | Политика кук; для HTTPS нужно `None` |
| `COOKIE_SECURE` | `false` | Флаг `Secure` на куках |
| `OZON_READ_TIMEOUT` | `60s` | Таймаут запросов к OZON |
| `SYNC_MATURITY_DAYS` | `3` | Окно зрелости: день окончателен, только если он старше |

Пустой `APP_ALLOWED_ORIGINS` — не заглушка, а решение по умолчанию: интерфейс
раздаётся с того же источника, что и API, поэтому CORS не нужен, а кука сессии не
покидает свой домен.

## Развёртывание на сервере

### Вариант 1. Docker Compose (рекомендуется)

Образ один и содержит всё: интерфейс, API и зависимости. На сервере нужны только
Docker и Compose.

```bash
git clone <репозиторий> analizer && cd analizer

# Настройки для боевого режима: пароль базы и HTTPS-куки
cat > .env <<'EOF'
DB_URL=jdbc:postgresql://postgres:5432/analizer
DB_USERNAME=analizer
DB_PASSWORD=<сложный пароль>
COOKIE_SAME_SITE=None
COOKIE_SECURE=true
EOF

docker compose up -d --build
```

Если интерфейс раздаётся напрямую по HTTPS, оставьте `APP_ALLOWED_ORIGINS` пустым:
источник один, CORS не нужен. Заполнять его нужно, только если фронтенд живёт на
другом домене или порту.

Данные переживают пересборку: база лежит в томе `analizer-pgdata`.

Перед публикацией в интернет замените пароль базы и обязательно включите HTTPS —
иначе незащищённый канал раскроет реквизиты OZON, которые приложение хранит у
аккаунта продавца.

### Вариант 2. Раздельно, фронтенд на своём сервере

Подходит, если интерфейс раздаётся через CDN или отдельный nginx. Тогда:

```bash
cd frontend && npm ci && npm run build   # получится один index.html
```

Положите его в корень сайта и укажите backend источник:

```bash
APP_ALLOWED_ORIGINS=https://analizer.example.com
COOKIE_SAME_SITE=None
COOKIE_SECURE=true
```

Без двух последних переменных сессия терялась бы на каждом запросе: браузер не
принимает `SameSite=None` без `Secure`.

### Обновление

```bash
git pull && docker compose up -d --build
```

Пересборка образа занимает несколько минут (Gradle и npm тянут зависимости),
повторные — быстрее: кэши живут в томах `analizer-gradle-cache` и Docker.

### Что стоит проверить после развёртывания

```bash
curl -fsS https://ваш-домен/actuator/health     # должно быть {"status":"UP"}
curl -fsS https://ваш-домен/                     # должен прийти HTML интерфейса
```

## Разработка

```bash
.\gradlew.bat test              # полный прогон, ~7 минут
.\gradlew.bat test -Pfast       # только модульные тесты, без БД, секунды
.\gradlew.bat bootRun           # запуск с текущим .env
```

`-Pfast` исключает интеграционные тесты `*IT`. Почти всё время полного прогона
уходит не на сами тесты, а на подъём Spring-контекстов и Testcontainers, поэтому
во время правки кода запускать полный прогон незачем.

Фронтенд:

```bash
cd frontend
npm run dev          # разработка с горячей перезагрузкой
npm run typecheck    # проверка типов
npm run build        # сборка для production
```

### Порядок работы с API

Контракт лежит в репозитории и проверяется тестом на совпадение с тем, что отдаёт
приложение. После изменения любого метода пересоберите его:

```bash
.\gradlew.bat test --tests "ru.analizer.contract.OpenApiContractIT" -Panalizer.updateOpenApi=true
```

Иначе сборка упадёт — и это лучше, чем обнаружить расхождение при сборке фронтенда.

Типы для фронтенда генерируются из контракта:

```bash
npx openapi-typescript docs/openapi.json -o frontend/src/api/schema.d.ts
```

## Проверка на настоящих данных

Тесты проверяют логику на фикстурах. Сходение с реальной выгрузкой OZON проверяется
отдельно, скриптом:

```powershell
.\scripts\check-api.ps1 -Base http://localhost:8080
```

Скрипт проходит полный цикл и сверяет итоги: сумма по дням, сумма по товарам,
разбивка расходов, отсутствие двойного счёта возвратов. Подробности — в
[docs/VERIFY.md](docs/VERIFY.md).

Коллекция Postman для ручного прогона: `postman/ozon-analizer-catalog.postman_collection.json`.

## Что стоит знать

**Не все нули означают одно и то же.** Отчёт за период, который не загружался,
возвращает `200` со статусом `NOT_LOADED`, а не нули. Отсутствие данных — это
состояние, а не сбой. По той же причине день загруженный, но ещё не окончательный,
отличается от окончательного: маркетплейс досчитывает возвраты и сумма может
измениться.

**Данные догружаются сами.** Пустую базу, недогруженные дни и историю перед текущим
периодом интерфейс загружает без участия пользователя. Повторный запуск при этом
безопасен и не расходует квоту зря: сервер сам берёт только те дни, которых ещё
нет. Логика и её ограничения описаны в
[frontend/README.md](frontend/README.md#автоматическая-догрузка).

**Расходы по товарам меньше дневных.** Часть расходов не относится к конкретному
товару. Разница приходит отдельным полем `unallocatedExpenses` и не растворяется по
товарам молча.

**Фильтр по автору находит разные написания одного человека.** Название приходит
от OZON как есть; полное имя, фамилия и варианты написания сопоставляются между
собой.

**Ключ OZON хранится в открытом виде.** Утечка дампа базы даст доступ ко всем
магазинам. Запланировано шифрование AES-GCM с мастер-ключом — помечено как
`TODO(#encrypt-credentials)` в коде.

**Один аккаунт на маркетплейс на пользователя.** Два продавца на одном OZON эта
схема не поддерживает: молча выбрать один аккаунт значило бы отдать данные не
того продавца.
